# 语音链路“前台说话 / 后台办理”改造方案（草案，未实施）

参考 OpenAI GPT-Live 的“前台语音模型 + 后台推理模型”分工，针对“工具调用后回复慢”。本文只是方案，没有改代码，也没有测量新数据；下面的耗时拆解来自代码阅读，具体数值要等阶段0实测。

## 现状：一轮带工具的回复要经过哪些串行等待

依据 `lib/voice/qwen-protocol.ts`、`lib/voice/verified-audio.ts`、`lib/voice/reply-review.ts`：

1. 用户停说后，`server_vad` 再等 1000ms 才判定一轮结束。
2. 回复1：模型可能先说一句等待提示，再流式生成工具参数。参数开始生成时音频静音。
3. 工具串行执行（`this.serial`）。业务工具本身是确定性逻辑，不调用大模型，预计较快。
4. 发送 `function_call_output` 并调用 `response.create` 生成回复2。每一轮工具调用都多一次模型往返；一轮最多 6 次（`turnToolCount>=6` 时停止）。模型自己依次执行 list/describe/run/amend，往返次数可能叠加。
5. **回复2实时生成、静音录制**：WebRTC 音频按实时速度传输，`VerifiedAudio` 用 MediaRecorder 录完整段才可播放。回复语音有多长，用户就先等多长。
6. `reviewReply` 再调用一次 planner 大模型复核（单次超时 15s，最多 2 次）。如果判为 repair，还要再走一遍第4–6步。
7. 复核通过后才开始播放录音，用户这时才第一次听到结果。

10-28 的实测记录（`continuation-stall-investigation-2026-10-28.md`）显示：一轮从开始到结束的中位数是 7.7 秒，最长 16.9 秒。这个数字没有拆分到上面各步。

和 GPT-Live 对比，主要差在三处：
- 前台不能一边执行任务一边说话（第2–4步）。
- 任务由语音模型自己一步步调用工具完成，而不是交给后台一次办完（第4步）。
- 先审核再播放，审核期间完全静默（第5–6步）。

## 不变的约束

- 授权、确认、页面认证和成功回执，仍由确定性逻辑和后台状态决定。语音模型和复核模型都不能放行。
- 成功动画和成功说法只能依据后台的真实沙箱结果；旧确认不能授权新任务。
- 设备播报与 Qwen 实时语音仍然互斥，不引入第二个 TTS。
- 用户插话会取消旧讲解；后台结果迟到时，只更新卡片，不再播报。

## 分阶段方案

### 阶段0：先测量（必做，其他阶段的前提）

- 在 `VoiceTrace` 中为每一轮记录这些时间点：`speech_stopped`、`response.created`、首个工具参数完成、工具结果返回、回复2首个文字增量、`response.done`、复核结论、开始播放。
- 新增一个固定脚本的浏览器测量用例，用假语音服务和固定耗时，用来确认埋点正确；再用真实 Qwen 跑 10 轮以上的固定话术，得到各步骤的中位数和 P90。
- 产出：一张耗时拆解表。后续各阶段按这张表排优先级，避免凭猜测优化。

### 阶段1：一次交给后台办完（对应 GPT-Live 的“交给后台”）

- 新增一个粗粒度工具，例如 `bank_delegate`，参数只有 `{utterance, taskId?}`。后台用现有的确定性解析（`inferFunction`、`extractParams`、`plans/decompose`、`dispatch`）一次完成识别、建立任务、保存字段和推进 Plan，并返回一份紧凑结果：实际状态、缺项、需要用户做的选择、下一步。
- 现有的 `executeLiteral`（直接执行字面指令）就是这个思路的雏形，可以扩展适用范围：后台解析把握高时直接走后台；把握不足或请求复杂时，退回现在的 `bank_function`/`bank_plan` 细粒度工具。
- 预期效果：每轮的模型往返从多次降到 1–2 次。回复2以后台返回的事实为依据，复核更容易一次通过，repair 也会减少。
- 风险：后台解析覆盖不全时，可能误识别业务。缓解：沿用 `business_mismatch` 和 `needs_user_choice` 的拒绝机制；把握不足时一律退回细粒度工具，不猜测。

### 阶段2：按风险分级播放（对应 GPT-Live 的“边说边干预”）

不再对所有回复“录完、审完再放”，而是按回复类型分级处理：

| 类型 | 判定依据（确定性） | 播放方式 |
|---|---|---|
| 等待提示、追问缺项、闲聊 | 现有 `waitNotice` 规则扩展；工具结果给出 `nextQuestion` 或 `missing`，且回复中没有数字和结果用词 | 实时播放，同时用流式检查守卫 |
| 解释、比较 | 现有 `isExplanationRequest` | 实时播放，同时用流式检查守卫；整段复核改为事后进行，不通过时补一句更正，并以卡片为准 |
| 报告金额、结果、成功或失败 | 工具已执行写操作或查询，或者回复里出现金额、结果用词 | 维持现状：静音录制，复核通过后再播放 |

**流式检查守卫**：
- 一边播放，一边按规则检查文字增量。出现不在后台事实白名单中的数字、金额、“成功/已到账/已提交”这类用词，或者出现被禁止的承诺时，立即静音并取消这条回复，改走现有复核和恢复流程。
- 守卫只做纯规则匹配，不调用大模型，每次文字增量都同步检查。
- 文字增量可能比音频晚到。用 Web Audio 的 `DelayNode` 把远端音频整体延后约 300–600ms（具体数值由阶段0测量决定），让守卫有时间在声音播出前拦截。
- 还有一点：如果守卫来不及，可能已经播出半个词。所以阶段2只用于不涉及结果和金额的类型，保留风险最高的“报告结果”类型继续先审后播。

预期效果：追问和解释类回复从“生成时长 + 复核时长”降到大约“首个音频包 + 设定的延迟”。

### 阶段3：轮次判定调优（小改动，最后做）

- 把 `silence_duration_ms` 从 1000 试调到 700 或 800。现有 `speechContinuations` 会把 1200ms 内拆开的同一句话合并，能部分抵消提前切分的问题。
- 需要核对 Qwen 是否支持语义 VAD；如果支持，比较它和固定静音时长的误切率。
- 验收：真人连续口述（含停顿、改口）时误切率不升高。这一项只能靠真人测试，用合成静音麦克风测不出来。

### 不建议做的

- **完全照搬全双工。** Qwen 取消工具续答后，会拒绝新的 `response.create`（代码第151行有注释）。在客户端模拟“工具执行中前台继续自由对话”，容易与现有的 epoch、打断和恢复逻辑冲突，收益也不确定。
- **取消“报告结果”类回复的先审后播。** 这是金额、结果说法上的最后一道护栏，和 GPT-Live 的通用对话场景不同。

## 验收

- 单元测试：`bank_delegate` 的识别、退回、拒绝分支；守卫命中与放行；分级判定；插话后迟到结果不再播报。
- 浏览器测试（用假语音服务）：分级播放时，音频元素的静音和恢复时机正确；守卫命中后取消回复且没有新的银行写请求；现有 `voice-isolation`、`failure-audio`、`card-narration` 回归测试仍然通过。
- 真实 Qwen 测试：用阶段0的同一套固定话术，对比改造前后的中位数和 P90。报告中注明使用的是合成麦克风，不代表真人听感。
- 金融流程：拒绝授权、改口、取消、失败和重复请求，各自至少一条路径。
- 单元测试和浏览器测试分开报告；没有执行的项目不报告为通过。

## 建议顺序与工作量（粗估）

| 阶段 | 改动范围 | 粗估 |
|---|---|---|
| 0 测量 | `diagnostics.ts`、`qwen-protocol.ts` 埋点，新增1个浏览器脚本 | 0.5 天 |
| 1 交给后台 | 新工具定义、后台路由、`qwen-protocol.ts` 分流、测试 | 1.5–2 天 |
| 2 分级播放 | `verified-audio.ts` 改为可选的实时或延迟播放，新增守卫模块，`qwen-protocol.ts` 分级逻辑、测试 | 1.5–2 天 |
| 3 VAD 调优 | 一行配置 + 真人测试 | 0.5 天 |

建议先做阶段0，再按测量结果决定先做阶段1还是阶段2。如果录制和复核占大头，先做阶段2；如果工具往返占大头，先做阶段1。

## 实施记录（2026-11-01）

用户选定在 Qwen 上模拟 GPT-Live 的 Responses 托管委托，先实施阶段1；阶段0、2、3尚未开始。

- 开关：`QWEN_DELEGATION=responses`，默认关闭。`/api/live/session` 返回 `delegation`，只读播报会话不启用。
- 前台：`SPEAKER_INSTRUCTIONS` 加上唯一工具 `bank_delegate`。之后的 `session.update` 继续使用前台提示词（`QwenConversation.instructions`），不会切回完整的工具提示词。
- 后台：`/api/bank/delegate` 调用 `runDelegation`（`lib/voice/delegation.ts`），由 `QWEN_PLANNER_MODEL` 带着原有 `BANK_TOOLS` 运行工具循环。每次调用都以用户原话为准，经 `toolAction` 映射，再经 `dispatchAction` 和 `commit` 执行，和 `/api/bank` 走同一套护栏。
- 停止条件：
  - 最多 6 次调用，超出即暂停；
  - 需要用户选择时停下，原样提问；
  - 结果未知时停下，不重放；
  - 已经提交过一步之后再失败，按结果未知返回；
  - 同一 requestId 重试时不再执行。
- 回复复核（`onReviewReply`）和先审后播都保持不变，所以本阶段只减少前台的模型往返，不改变播放把关。
- 验证：新增 `tests/delegation.test.ts` 共 8 项；`npm test` 356/356 通过，`npm run check`、`npm run build` 通过。未运行浏览器端到端测试，没有开启开关连真实 Qwen 测试，延迟也没有测量。
