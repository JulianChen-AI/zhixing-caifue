# 鹅豆：业务模块 → 用户功能 → Checklist 编排 → 工具调用

版本：v2，2026-10-22。性质：功能与工具组织方案；当前只重组文档，不修改业务代码或开放工具。

## 1. 四层定义

| 层次 | 定义 | 示例 |
|---|---|---|
| 业务模块 | 一组相关业务的归属 | 智能转账、账单分析、订阅代扣、理财、卡片管理 |
| 用户功能 | 用户能够提出并得到明确结果的目标 | 发起转账、查询余额、查看卡片列表、挂失卡片 |
| Checklist 编排 | 实现目标的参数、依赖、条件分支、等待点及完成判断 | 解析对象 → 缺项补齐 → 检查 → 确认认证 → 提交 → 核验 |
| 工具调用 | 编排步骤调用的可复用能力 | 查询余额、选择收款人、整理备注、更新草稿、请求确认、请求认证 |

**同一底层能力可被多个功能复用。** 用户直接说“查余额”进入 TR02；办理转账 TR03 时，也使用 T02 余额查询工具。用户功能不等于工具函数、接口或独立页面。

备注、账户/收款人选择、风险检查、确认、认证、回执生成、字段隔离均归入编排或工具层，不再与“转账”“挂失”并列成用户功能。账户列表、余额查询放在 M1，作为五模块共用的账户入口；不据此增加第六业务模块。

本稿按当前任务粒度组织为 **54 项用户功能**。数量只用于索引，不作为开发量指标；54 项也不代表 54 个独立页面。旧 79 条索引完整映射到新功能、公共步骤或工具，见第 11 节。

## 2. 可选参数、条件步骤和可选能力

### 2.1 三种状态分别处理

| 类型 | 判定依据 | 留空或未触发时的行为 | 示例 |
|---|---|---|---|
| 入口允许暂缺、执行前必需的信息 | 业务规则 | 可先进入草稿，执行前必须补齐并有来源 | 收款人、付款账户、金额 |
| 真正可选的参数或增强项 | 用户表达和当前参数 | 未提供则使用明确默认值或跳过；不为了凑齐表单逐项追问 | 备注、保存联系人、PDF 导出、年度叙事 |
| 条件触发的步骤 | 后台事实、通道能力与动作策略 | 条件成立才调用；条件不成立跳过步骤，要求仍由后台检查 | 多候选才选择；已有有效同用途授权则不重新申请；按动作要求认证 |

在第 4–8 节工具标记中：**〔必需〕**表示该路径的必要能力；**〔条件〕**表示条件满足才调用；**〔可选〕**表示附加能力，由参数或用户明确需求开启。它们不是允许模型随意删步骤的开关。一次功能可能有多个 action，标记结合当前 action 解释。

“必须满足某条件”和“每次都发起一次新工具请求”分开：资金执行必须有可信且满足时效规则的余额依据；同一可信快照仍有效时，可复用而不重复查询。已有明确对象也不必重复弹选择卡。

### 2.2 备注的建议参数设计

首先采用 `note?: string | null`，避免同时传 `needNote` 与 `note` 造成矛盾。

| 输入 | 创建草稿 | 修改已有草稿 |
|---|---|---|
| 未传 `note` | 不添加备注，不追问备注，不调用备注整理 | 保留旧备注，避免误清空 |
| `note: null` | 不添加备注 | 明确清空备注 |
| `note: "饭钱"` | 使用用户有依据的文本，必要时整理/检查 | 替换为当前有依据的文本 |
| 仅说“帮我想个备注” | 可生成建议，标注来源并让用户看见/修改 | 同左；不能伪装为用户已说过的话 |

空白字符串可在参数规范化时视为清空；未知或含糊的值不能装成明确备注。即使备注整理工具未触发，后台仍对实际存在的字段执行格式、敏感信息和指令隔离检查。

其他附加参数也直接表达需要的结果：`saveRecipient?: boolean` 默认 false；`receiptExport?: "pdf" | null` 默认无导出；`peerComparison?: boolean` 默认关闭。初期不增加一套冗余“是否需要”字段。

**用户明确提出的附加条件必须兑现或说明无法完成。** 用户说“必须备注房租再转”，备注成为本次任务约束；用户要求 PDF 导出，而导出工具不可用，应说明导出失败，不能假装已生成，也不能因此重新转账。

### 2.3 参数化 checklist 调用示例

以下是建议调用合同，尚未实现为代码接口：

```ts
runChecklist("TR03", {
  recipient: { query: "室友张三" },
  accountId: undefined,     // 可先留空，执行前需要明确
  amount: 500,
  note: null,               // 无备注；不用追问
  saveRecipient: false,
  receiptExport: null
});
```

后台据此展开步骤：

1. 已有明确且获授权的收款人则复用，否则调用 T03；候选不唯一才调用 S02。
2. 缺付款账户时取 T01，并通过用户原话/选择补齐，不默认选一个。
3. 本例无备注，不调用 T16；T05 保存其他有来源字段。
4. T02 按余额依据的有效性决定是否重新读取；T06 检查资金、风险和通道。
5. 按后台动作规则经过 S05 确认及 S06 认证；模型不能传 `skipAuth` 或 `balancePassed` 来放行。
6. T07 受控提交；从结果或 S08 得到真实状态，得到完成证据才报告成功。
7. 本例不保存联系人、不导出 PDF；后台仍记录必要办理事件。

### 2.4 工具缺失的降级

- 必需能力缺失：暂停并说明缺什么，不能用模型回答冒充执行。
- 可选能力未请求且不可用：不调用，不阻断基本功能。
- 可选能力已请求但不可用：说明具体限制，保留已完成业务，提供可行后续。
- 条件能力缺失且该条件触发：停止相应路径或使用事先定义的降级路径。例如外部深链不可用时提供官方步骤；不能删除认证来降级。

范围标记：“基础”是模块基本办理能力；“完整”是原文完整范围内的后续功能；“扩展”是可后置的展示/高级能力。此分类用于分期，不自动删掉原始需求。

每个功能均按以下公共约定执行，下文不机械重复：

- 用户身份、权限、规则、账户和产品事实由后台读取；模型仅提出有依据的参数。
- 明确的参数不重复询问；真正的歧义才澄清。工具候选不唯一时等待选择。
- 查询只需适当数据授权，不因为存在通用确认工具而每次要求交易式确认。
- 写动作在其规则要求的节点等待明确确认/所需认证；改对象、金额、重要后果或关键参数使旧确认失效。
- 原始口语、卡片修改和工具结果有来源引用；函数格式合法不能替代来源核对。
- 每次状态变化及必要拒绝事件由 S11 后台记录；模型不可自行写“检查已通过”。
- 结果区分草稿、等待信息、等待确认、等待认证、已受理、处理中、已完成、失败、未知、已取消；具体业务有自己的细状态。
- 发生超时先查询结果再决定能否重试；同一请求幂等，已成功步骤不重复执行。插话取消播报与取消已提交业务分开。
- 结束以真实工具结果为准；外部页面返回、用户自报、协议状态和流水观察分别保存来源，不混为同一种成功。

当前能力静态核对：TR01/TR02 基础演示可用；TR03 仅固定合成联系人及即时模拟主链；TR07 仅取消未完成草稿。其余新功能未接通对应执行器。下文所有工具名为设计别名，不是在本次重命名当前代码。

## 9. 工具目录：复用能力及可选触发

这些是逻辑工具，不要求逐个制作 HTTP 接口或全部直接开放给 Omni。受控编排可以调用后台内部函数、程序计算或 UI 中介；同一工具家族可用白名单 `action` 区分动作。具体 action 的参数、权限和副作用须分别校验，不能变成任意数据库访问入口。

**基础合同**：输入 = 业务参数 + 来源引用 + 后台绑定身份 + 状态版本；输出 = 实际数据/状态 + 来源/时间 + 缺项/不确定性 + 结果编号。模型可选择是否请求可选能力，后台负责确定条件、权限及执行资格。

当前用户可调用接口仍为 `bank_request` 的六个 operation：`get_state`、`list_accounts`、`update_transfer`、`confirm_transfer`、`cancel_transfer`、`select_workflow`。例如 T01/T02 可从 `list_accounts` 既有能力适配；T05 可复用 `update_transfer`；S05 与 `confirm_transfer` 对接；S06 仍为页面认证。设计工具和现有 operation 不要求一对一。

## 10. 动态任务如何复用四层结构

### 固定用户功能

`用户目标 → 选择功能 ID → 读取对应 CL-功能ID → 用明确参数展开条件步骤 → 调用工具 → 保存实际结果`。

不需要每句普通对话都调用后台规划模型。Omni 可自然询问缺项、处理改口和闲聊；复杂组合才交给后台规划。

### 复合任务

示例：“查一下余额，够就转账，剩下的钱买一点基金。”

| 粗步骤：用户功能 | 对应 checklist | 工具与后续依赖 |
|---|---|---|
| TR02 查询余额 | CL-TR02 | T01/S02 按需明确账户 → T02，取得可信余额和时间 |
| TR03 发起转账 | CL-TR03 | 使用明确金额判断余额；缺收款人/金额就问 → 完整转账检查及确认/认证 → 实际结果 |
| IN06 查询产品 | CL-IN06 | 转账后重新确认真实可用余额；明确“买一点”的金额及用户选择；I07 提供候选 |
| IN08 购买产品 | CL-IN08 | 有效画像和适当性检查 → 费用风险说明 → 对应订单自己的确认/认证 → I12/I13 实际状态 |

后台任务计划需要记录：`functionId`、`checklistVersion`、`args`、`dependsOn`、可信结果绑定、`when`、等待点及失败处理。模型提出计划，后台验证工具/功能白名单及条件表达式后运行；不执行模型生成的任意程序代码。

规划器不是第六业务模块，工具注册表/计划管理也不混进五个模块的用户功能目录。建议后台接口家族为 `capability.list`、`checklist.get`、`task_plan.create/validate/advance/replan/status/cancel`，与理财定投的 `investment_plan.*` 分开。

若转账成功而基金购买失败，报告部分完成，只恢复失败/未完成部分。动态生成的计划不能因为省略确认节点就越过业务工具的固定门槛。若某项可选参数不传，只裁剪该项允许省略的步骤。
