## 真实 Qwen 运行证据

参考聊天“梳理鹅豆项目现状”的方法，复用现有服务端配置、本机 Chrome 和配套 Playwright，通过 Windows SAPI Huihui 生成中文 WAV，再经音频流注入 WebRTC。测试没有读取或打印真实密钥。

两个独立会话 `b / c` 均完成以下路径：

1. 语音“请查询二零二六年十月的餐饮支出”：调用 `bank_function` 的 BI02，后台毛支出 64 元、退款 12 元、净支出 52 元。实际模型字幕正确说明净支出 52 元。
2. 同一原生会话中键盘输入查卡片，调用 CA01。
3. 插话“等等，先查看我有哪些订阅”，调用 SU01。
4. 创建“毕业旅行”目标，3000 元，2027-06-01，不自动存钱：IN01 只建立待确认草稿；未索要账户或周期。
5. 用户明确确认后调用 `bank_function` 的 confirm：只创建一个目标，余额 0，自动规则数为 0。会话 `c` 另验证完成结果回传后模型播报“目标已创建”。
6. 结束会话后音轨和 PeerConnection 已释放；无供应商错误事件或浏览器脚本错误。

调试期间曾出现语音确认超时，后台保留待确认状态，没有错误执行。会话 `final` 捕获到一个明确失败样本：供应商确认参数缺少末尾括号，桥接层无法解析，业务 HTTP 未执行。这个证据可以解释该样本，不能据此认定所有早期失败只有同一原因。

后续增加了真实终态参数读取：若 arguments done 不完整，只等待输出项的真实终态参数，不猜补括号、对象编号或令牌。若终态也不完整，回传 `invalid_tool_arguments / effectCommitted:false`，并显示非中断提示、明确重试或页面办理路径。已向后台发出的请求若结果无法解析，则返回 `tool_result_unknown`，不声称未执行。相关参数等待、打断及未知结果边界已加入自动回归。

修复后的 `recovery` 会话完成八项检查。该会话再次出现一次截断的确认令牌，供应商终态也同样不完整；桥接层明确拒绝执行并返回错误，模型随后重发完整 confirm。最终仅创建一个目标、没有自动规则，完成结果已播报，音轨和连接已释放。这验证了实际错误恢复路径，仍不能证明模型今后不会再次给出不完整参数或长期会话永不失败。

会话 `c` 出现一次不完整 JSON 参数。桥接层拒绝执行并返回错误结果，随后模型重试完整参数并完成办理；六次供应商调用中五次进入业务 HTTP，目标仍只创建一个。这说明失败恢复路径生效，不应表述为每个模型调用都一次成功。

本次未发布站点，未连接银行/商户/发卡机构、市场行情或系统推送。演示问卷不是正式机构适当性资格；模拟受理、模拟结算及页面演示认证不能替代真实机构流程。
