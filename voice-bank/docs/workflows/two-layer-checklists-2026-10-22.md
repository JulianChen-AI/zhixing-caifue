# 简单单层、复杂双层任务清单

日期：2026-10-22。实现位于 `fix/live-page-close` 分支；尚未部署服务器。

## 执行方式

| 请求 | 执行路径 |
| --- | --- |
| 从日常账户给室友转500元 | 原业务清单，直接补字段、核对、确认及页面认证；不增加外层 |
| 给尾号6688的张三转余额较小账户的三分之一 | 外层：读取余额 → 比较/计算 → 转账；转账节点再走原内层业务清单 |
| 先转500，再拿剩下500整理材料 | 外层保留所有步骤，未明确用途的节点要求补充；用途明确前不提前扣款 |
| 先转500，再存500到旅行目标 | 两个顺序节点分别运行各自业务清单，前一步完成才放行下一步；每一步分别确认，按原规则认证 |

外层是保存到会话的可执行状态机，包含步骤ID、前序依赖、来源原话、实际子任务ID、状态、计算依据和事件记录；不能由模型填写passed或complete。内层继续复用已有用户功能目录、字段来源检查、余额/风险/限额、摘要令牌和认证执行器。两层最终由同一次会话revision比较并原子保存，不增加第二份资金执行器。

只读步骤和计算可由程序继续推进。写步骤停在对应review/authenticate，不因整个任务包含“先……然后……”就直接授权全部操作。原来已完成的步骤不重复运行；新的字段或动态事实变化，只影响相应后续步骤。

## 拆解与连续对话

- 原生语音新增 `bank_plan` 工具，提供create/amend/status/pause/resume/cancel。现有Qwen继续理解语音，可提供按原话划分的业务功能建议；本次没有新增第二个语言模型。
- create可省略steps，由后台识别常见转账、账户、账单、订阅、目标、卡片请求。复杂请求误送旧update_transfer/run时，接口会转入外层拆解，避免重新陷入旧金额校验循环。
- 显式steps必须按顺序覆盖全部子句，不能丢掉未知用途；业务模块与原话、字段值与原话分别校验。未知用途保留为clarify，模型不能用一个无依据的功能编号把它标记为明确。
- 简单请求继续原入口；“500，然后改成300”这类改口不被创建为两笔业务。
- 文本入口和页面可补充步骤用途；当前内层字段仍由现有业务卡片修改。native工具使用当前planId/stepId/taskId，不为每次补充重建整条任务。
- 页面显示办理顺序、已完成数量、依赖、计算解释、补充用途及暂停/恢复/取消按钮。刷新重新读取同一计划与子任务ID。

## 计算依据

账户比较、明确账户的余额比例由后台读取实际合成账户余额，使用整数比例和分币计算，向下取整到分。示例初始日常余额为1,286,500分，除以3得到428,833分，余1/3分；核对金额为4,288.33元。结果包含账户、原余额、分子/分母、取整方式、余数、余额快照和revision，并作为内层amount/accountId的calculation来源保存。

余额相同不代选；用户明确账户后继续。确认或认证前再次比较余额快照，变化时重新计算、撤销旧确认/认证、返回新摘要，本次不扣款。用户明确改为固定金额时可覆盖绑定，不再假装该固定金额仍随原比例变化。

## 顺序、失败和授权

- 内层操作只能作用于当前外层节点的子任务，不能通过旧转账入口、新run或另一taskId跳过依赖。
- 每个新摘要需要新的确认。native调用携带实际用户turnId；不能用创建任务时的发言、上一笔的确认，或修改金额的同一轮发言授权新摘要。页面确认本身是独立用户操作。
- blocked、取消的节点、未接入能力及external会停止后续步骤；暂停后原子业务修改也被阻止。
- 申购/赎回受理后pending不当作到账。实际沙箱订单settled后才放行依赖；外部办理结果不能由模型口述标成完成。
- 后一步启动失败保留已经认证完成的前一步和回执，不回放扣款。取消只取消剩余步骤，已完成/已受理结果保留。
- 原requestId幂等和revision并发检查保留，模型工具链6次保护也保留；外层调度本身最多推进12个节点，不依赖模型不断查询状态来推进。

## 当前范围

这是针对现有银行目录的受控顺序拆解器，支持线性依赖；不明确的用途需要人补充，不等于任意自然语言任务都可自动执行。每次最多6项业务，加入计算后最多12个节点。沿用现有适配器能力，未接入的材料导出、外部通道等仍明确停止，不会通过“拆解”伪造完成。

现有未完成转账需先完成或取消，再建立新复杂清单。计算支持明确余额的分数、百分比、一半和全部；新比例应明确，不接受多个相互竞争的比例。任意条件分支、并行资金操作、跨外部服务事务未在本轮实现。
