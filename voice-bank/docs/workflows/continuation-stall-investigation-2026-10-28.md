# 续答停滞定位与上下文重开（2026-10-28）

后续调查及最新验收见[解释/查询隔离与最终快照接续（2026-10-29）](reply-isolation-and-final-snapshot-2026-10-29.md)。本文保留当时的故障与测试结果，不作为后续版本已全部修复的依据。

本记录接续[上轮复核与恢复验收](verified-reply-recovery-2026-10-28.md)。结论区分自然故障、受控实验和预防措施。以下均为新建本地合成会话；没有重放捕获的用户状态，也没有测试真实银行或真人麦克风。

## 目前能定位到哪里

1. **没有证据表明原失败就是上下文已满。** 历史失败前最后成功响应的输入量分别约21,921、35,637、58,151 Token。上轮成功44轮的峰值反而达到84,281。官方当前型号输入上限为196,608，并说明历史超限会自动截断，本轮单条输入超限才报错。输入计量是当前窗口，不能将历轮账单Token相加当作窗口占用。未达硬上限不能排除复杂/长上下文对指令遵循、推理质量或服务稳定性的影响。[官方上下文说明](https://help.aliyun.com/zh/model-studio/realtime)
2. **部分自然故障发生在供应商已接受生成请求之后。** 原wire记录显示客户端已发送输入/工具回执与`response.create`，收到`response.created`，之后长时间没有有效完成，最终是本地30秒watchdog关闭连接。另一例在第36轮确认工具发出前收到`Receive batching backend response failed!`，后台仍为review。协议遗漏、业务未提交和生成收尾失败不能混为一谈；提供方内部推理/事件投递的进一步区分需要其服务端按response ID追踪，客户端不能证明内部原因。
3. **单条传输尺寸是另一个已复现的限制。** 本次真实连接协商的DataChannel最大消息为65,536字节。向`session.update`一次塞入60,000字符合成背景，实际JSON为156,413字节，浏览器在`send`直接抛`Trying to send message larger than max-message-size`。这时没有`session.updated`，更谈不上模型上下文溢出。旧发送链未捕获此异常，异步工具链可能停留到watchdog。这个缺陷已修，但原自然故障中已经收到`response.created`的样本不能据此归因为超大消息。[WebRTC消息尺寸说明](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Using_data_channels)
4. **两个模型一致仍可能判断错误。** 中间复测中，Omni对“只比较产品，不申购”的解释本来相关，Flash却因活动问卷未完成而要求继续/提交问卷。另一次冻结草稿已存在，但遗漏明确的action，Flash仍放行。这两类会让用户感到没有完成本轮要求，属于意图/保存判断问题，不是连接停滞。本轮禁止纯解释分支提出业务修正，并要求草稿保存所有可独立解析的明确字段，而不只核对对象ID。
5. **新诊断捕获过网络断开，不应误判为模型生成卡住。** v3在第25轮前有12轮/30,168输入Token；最后一次输入发出后尚未收到`response.created`，诊断为requested=true、pendingTools=0、reviewPending=false、sendFailed=false、ICE/PeerConnection均disconnected，DataChannel名义上仍open。随后测试某轮elapsed达到2,339,592ms（约39分钟），超出75秒测试上限，说明测试执行/时钟存在长空档。Windows只读事件查询未取得可证实休眠的对应记录，不能断言是休眠，也不能归因于模型上下文。新测试增加>15秒轮询空档检测，出现时标为inconclusive；最终复测期间只临时请求系统保持运行，结束立即释放，不改电源设置。

自定义工具的基本接续顺序仍为回填`function_call_output`后发`response.create`，与[官方协议](https://help.aliyun.com/zh/model-studio/client-events)一致。此前新建短会话中原样5649字符回执也曾2/2自然续答成功，不能说“大回执必然卡住”。主动取消后的工具轮次直接续答被拒绝，是另一个已实测的协议约束；恢复不再继续被取消的旧轮次。

## 实现的缓解

- `session-context.ts`：去掉工具返回在外层Plan中的重复结果副本，保留本次operationResult完整结果、Checklist、Task ID和确认请求。目录54项完整保留。没有拆开或拼凑协议JSON。
- 正常会话达到60,000输入Token、24个用户轮次或15分钟后，在下一轮输入且没有业务请求/复核待完成的边界重开。这些是保守的软阈值，不是测得的失效阈值。ASR若已发起工具则推迟切换，不重放该工具。
- `/api/live/context`为只读摘要端点。Flash只压缩主题、表达偏好和未解答的一般问题；Task ID、参数、问卷答案、金额单位、当前结果与状态由后台快照恢复。历史摘要不是新授权，不能确认、认证或重做已完成步骤。Flash不可用时仍用确定性的后台快照；摘要后再读取最新revision，旧快照不得覆盖新状态。
- 发送前检查UTF-8字节数及协商上限，捕获`RTCDataChannel.send`异常，立即进入同一有界恢复；工具已发起/结果未知时只读核对，不重放。不会静默截断业务结果或把未送达当成已完成播报。
- 本地`sessionStorage.zx_voice_diagnostics`保留最近6次元数据诊断，每次最多80个事件：响应阶段、输入/输出Token、等待状态、传输状态/缓冲字节、协商尺寸及错误分类。没有正文、工具参数/结果、金额、认证令牌或密钥，不上传诊断。后续可据此区分“未发送”“已接受生成但无完成”“等待工具”“等待复核”“等待配置确认”。
- 若Omni漏掉对当前未执行冻结草稿的明确取消，严格字面取消解释器可走与页面相同的原后台接口；仅绑定当前CA06冻结草稿、保留原话、检查未执行状态。问题、否定取消、其他对象或已完成业务均不代办。Flash仍不能提出或授权cancel。此路径报告为literal，不冒充模型调用。
