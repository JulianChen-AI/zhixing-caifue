# 业务检查单目录

来源：用户提供的四份设计文档，快照见 [sources/manifest.json](sources/manifest.json)。当前 62 条流程、269 个检查项。规范数据仅维护在 [catalog-data.json](../../lib/checklists/catalog-data.json)，界面和后端读取同一结果。

## 当前执行范围

- 按人名模拟转账、查询演示账户余额已接执行器。
- 账单、订阅、理财及扩展转账流程已建规则定义；选中后明确返回“执行能力未接入”，不会伪造业务结果。
- 已存演示联系人均标记为有历史往来的合成联系人。本地 v2 产品演示覆盖策略允许金额上限内即时模拟（含 500 元），不连接真实支付。文档的 200 元示例不再作为默认硬门槛；延迟结算和升级核验仍未接入，风险信号继续阻断。此覆盖策略记录在 demoPolicy.thresholdSource，不能用于生产银行业务。
- 收款人、金额、付款账户和最终确认均可通过语音明确，卡片同时显示结果；仅演示认证必须通过页面。原生 Omni 理解上下文后可直接提交没有单位的明确金额（500、500。、五百），后台核对数值，不额外循环确认；多义或冲突才澄清。旧离线文字入口保留原先的单位追问。账户列表查询保留当前草稿和认证；可按账户名、尾号或可见列表序号选择，不使用默认账户。原生语音确认校验用户明确确认和当前 reviewToken，再调用与按钮相同的确认执行器，模型不能自行授权。

## 两步流程

1. 意图识别检查：业务唯一、字段来源可核对、没有未解决歧义；返回 proceed / clarify / blocked / unsupported。金额、联系人和付款账户由原话或当前已明确任务佐证；模型选了合法 ID 仍不能代替佐证。
2. 执行检查单：逐项检查，第一项未满足即停止，后续标记 pending。前端显示与后端判断共用规则结果。卡片操作更新字段后重新检查；修改使旧确认与认证失效。

未知意图会追问；多业务请求先让用户明确一项；不支持的业务展示选中的清单与缺失能力。敏感认证信息不写入意图证据。高风险词命中后不以一项“我确认安全”绕过未接入的升级核验。

## 逐步说明与记录

每次成功保存的状态变化连同规则版本、请求 ID、所选流程、规则通过/暂停原因、字段来源和前后步骤一起保存。数据库 revision 条件更新保护并发，相同请求 ID 不重复扣款或重复记事件。演示记录保留最近 100 次，重置会清除；这不是机构级不可篡改审计或长期档案。被接口格式校验或错误认证直接拒绝的请求目前仅返回错误，不纳入这份业务状态轨迹，后续应补独立拒绝事件存储。

## 从文档提炼时的取舍

- 低额语音确认与统一显式确认：本版接受当前转账摘要之后的明确语音确认，仍必须在页面完成演示认证。
- “取消订阅”统一先走订阅场景；账单洞察只能移交，不能顺便取消协议或操作资金。
- 解除银行代扣、商户退订、退款分别建模。通道不支持跳转时使用经验证的分步指引，不承诺已取消。
- 提醒与持续扣款分别授权；提醒到期不自动成交。风险测评与投教、成长值分别处理。
- 收益和费用来自数据工具；估算必须披露假设。异常只列依据，不直接定性。
- 法律条文、统计数字、竞品结论保留在原始快照作为团队输入，未当作已核验事实或直接转成硬编码法规。
- FATE、企鹅成长、模型自报置信度不作为当前已实现能力。所需适配器和产品参数须单独验收。

## 后续接入约定

同伴增加适配器时，先补真实/沙箱数据来源和事实字段，按清单评估，再通过固定 action 执行，工具成功后才生成回执。不要通过把字段写成 true 来绕过缺失适配器。CI 应覆盖每个停止条件、明确授权、变更失效、异常回滚与来源引用。

相关代码：`lib/checklists/routing.ts`（意图策略）、`evaluate.ts`（顺序检查）、`lib/bank/engine.ts`（当前转账适配器）、`components/checklist-explanation.tsx`（解释面板）。

查看年度报告与分享报告已分成不同清单。可选功能关闭是明确的安全选择：不生成同龄分位、不分享、不启用自动储蓄时，不要求对应的额外权限。适配器必须用真实上下文判断这些条件，不能把缺失字段当作用户已同意。`stage` 区分前置检查、授权、确认、认证和事后回执核验；回执属于事后条件，不能要求用户先提供回执才能发起业务。
