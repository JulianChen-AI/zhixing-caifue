# 第一部分 · 我们要做什么（TL;DR）

**一句话**：让年轻人"关系型的钱"体面前行——说一句话就完成找人、转账、定时、AA 收款；Agent 把催款的社交压力、转错的风险、被骗的可能全部接过去。

> **内部视角校准（v2.4，董小峰会议）**：转账被内部定位为**低频常规交易**（"天天转账我怀疑你洗钱"）、创新空间有限——本场景的战略分工据此明确：**不做创新主打，做任务完成率 40% 的稳定拿分场景 + 安全合规主场**（防骗/防错/防催款的护栏设计是得分点），创新资源向理财操作与账单分析倾斜。声纹相关设计按会议结论校准：声纹只能**证伪不能证明**，仅作低风险辅助（盲人场景结合人脸），防御基础是终端可信（常用设备/IP/GPS）。
>
> **行为设计学锚点（v2.5，理论层见《行为设计学理论层》）**：**有限注意力**——"找人/核对卡号/想备注"是纯注意力负担，Agent 把它外包（说人名就转）；户名核验防的正是**注意力失误**（转错人大多不是被骗，是没注意）——把认知负荷压到最低是本场景的设计原点。**过度自信**——"我记性很好不会转错"→核验式确认温和兜底：不挑战自信，只兜住失误；"不好意思催款"的社交自信（"我下次一定记得要"）→群代催把尴尬外包给规则，承诺机制在社交场景的应用。

**产品定性（v2.3 钉死，外部挑刺 A2）**：知行语音银行是**微众银行的智能交互层**——Agent 只负责理解、规划、确认和留痕，所有资金划转、账户、KYC 均复用微众现有持牌能力；本方案不新增任何支付/收单/清算主体。评委问"这是银行功能还是你们自己的转账系统"，答案就是这一句。

**目标人群**：年满 18 周岁的在校大学生（大一至研二）+ 初入职场新人（毕业 0-3 年）——与理财场景同一人群、同一财富鹅人格，转账是"高频入口场景"（日均使用），理财是"价值深化场景"（资产沉淀）。

**五大子任务**（赛题原文点名）：按人名转账、按手机号转账、备注转账、定时转账、拆分 AA 收款。

**三大功能支柱**：
1. **找对人** —— 人名消歧 + 户名核验式确认 + 关系分层，从源头消灭"转错人"
2. **AA 全托管** ⭐创新主点 —— 规则前置 → 智能拆分 → 跨平台发出 → **阶梯代催** → 收齐汇总：*"把催款的社交压力转移给 Agent"*
3. **周期资金日历** —— 定时转账升级为"工资日/还款日/房租日"同历管理 + 执行前余额校验 + 电子回执

**两道安全闸**（本场景是安全 30% 分的主战场）：
- **防转错分级确认**（P0-4）——熟人小额一句话，新收款人/大额升级 TOTP + **默认延迟到账（窗口内可撤销）**
- **防骗雷达**（P0-1）——规则+LLM 双通道识别诈骗话术，命中后升级处置而非粗暴拒绝

**评审点命中**：任务完成率 40%（人名消歧→回读→确认多步规划链）+ 安全合规 30%（P0-1/P0-2/P0-4 三大安全点全部落在本场景 + T-R1~R10 红线总表）+ 创新性 30%（AA 全托管、备注语义化与条件触发定时两个全行业空白）。

# 第二部分 · 赛题场景拆解

## 2.0 五个子任务 ↔ 解法对应

| 子任务 | 本质问题 | 用户卡点 | 我们的解法 |
|---|---|---|---|
| 按人名转账 | 自然语言 → 唯一收款账户 | 通讯录三个"张伟"；重名不敢转 | 联系人解析 + 歧义追问卡片 + **收款人逐字回读** |
| 按手机号转账 | 无联系人关系的精准定位 | 手输怕错一位；旧号二次放号 | 号码校验 + **户名核验式确认**（掩码回显；姓氏补全为可选加强，v2.3——不知道全名不卡死，走升级确认通道）+ 新收款人升级确认 |
| 备注转账 | 钱的"用途语义" | 备注手输麻烦、事后看不懂 | 语音摘要 + **八类模板** + 分类标签（暗线喂账单场景） |
| 定时转账 | 未来的钱按计划走 | 房租/还款/承诺全靠自己记 | 一句话建规则 + **资金日历** + 扣款前余额校验 + 电子回执 |

## 2.1 按客户旅程的完整业务拆分（转前 → 转中 → 转后）

> 对齐理财 2.1 的方法论：赛题五子任务是"点"，真实转账业务是一条旅程。

### 转前（找人与决策）
| 业务 | 任务流 | 说明 |
|---|---|---|
| 联系人解析与消歧 | TF-T01 | 人名 → 候选 → 追问 → 唯一收款人；历史对象优先 |
| 手机号定位 | TF-T02 | 号码校验 + 户名核验式确认 + 新号/换绑风险提示 |
| 收款人/别名管理 | （contact.manage） | 别名设置、关系分层（好友/房东/陌生人）；字段注入隔离 |
| 防骗前置检测 | TF-T08 | 对话一开始就在跑的雷达（硬软双通道） |

### 转中（执行与留痕）
| 业务 | 任务流 | 说明 |
|---|---|---|
| 分级确认路由 | TF-T09 | 按金额/关系/时段路由到不同确认强度与结算方式（阈值矩阵） |
| 备注生成与过滤 | TF-T03 | AI 摘要+模板+敏感词双通道（模板白名单豁免）+"AI 建议"标识 |
| 定时规则创建 | TF-T04 | 周期规则 + 资金日历注册 |
| AA 发起与改算 | TF-T05/T06 | 规则前置 → 拆分 → 自然语言改算 → 发出 |
| 执行与留痕 | （所有） | audit_logs 全链路：指令原文/验证方式/AI 摘要/确认/时间戳，10 年追溯 |

### 转后（对账与善后）
| 业务 | 任务流 | 说明 |
|---|---|---|
| 撤销与延时窗口 | TF-T10 | **已到账资金不可单方撤回**（支付铁律）；可撤销的是"延迟结算窗口内未执行指令"——熟人小额可选「可撤销转账」（延迟 2h），新收款人/大额默认延迟到账天然带窗口 |

| 定时任务执行前校验 | TF-T04b | 扣款前 3-5 天余额检查；失败即停不自动重试 |
| 电子回执与凭证导出 | TF-T11 | 回执生成/PDF 导出；押金/报销/借款的举证支持 |
| 对账与关系账本 | TF-T11b | "我借出去多少、谁还没还"月度清单；对接账单分析场景（《账单分析场景·设计文档》v1.7 已建成，BA-B04/人情账本联动，v2.3） |
| 争议与冲正 | （边界声明） | 错账冲正、撤销、补备注流程（复用微众现有客诉体系） |

# 第三部分 · 需求依据

## 3.1 核心洞察

目标人群的摩擦不在"有没有移动支付"（网络支付用户 **10.22 亿**、渗透率 91%，CNNIC 2025-06；18-40 岁占移动支付用户 65.3%），而在**关系型转账的软性成本**——催款的情面、转错的灾难、周期的注意力占用、争议时的举证无门。

**设计总纲**：好的智能转账不是让青年更敢花钱，而是——**敢花的小钱不伤关系、该准的大钱不出错、周期的事不占用注意力、出了争议拿得出凭证。**

## 3.2 三层人群 × 核心痛点

| 人群 | 高频场景 | 最迫切需求 | 核心痛点 |
|---|---|---|---|
| 大一–大二（校园关系高频层） | 宿舍拼单、班级聚餐、社团、班费 | 群内低尴尬 AA + 自动代催 | 垫付后不好意思催，"每次都要有人做坏人"；社交娱乐占生活费去向 41%，AA 是群体身份维护而非纯财务动作 |
| 大三–研二（过渡层） | 实习通勤、科研垫付、毕业旅行、异地恋 | 转账前身份确认 + 备注凭证 + 周期提醒 | 给新同事/房东/中介转账怕转错；垫付报销怕说不清；报销/借款/赠与混在同一账单 |
| 职场新人 0-3 年（责任陡增层） | 房租押金、合租水电、还款、人情随礼 | 周期自动化 + 余额校验 + 电子回执 + 大额保护 | 合租与押金纠纷高发（v2.3 修订 F3：原引"合租比例 54%/押金纠纷 33.3%"无可靠出处，**已删除具体数字，答辩不使用**）；逾八成受访者称份子钱有压力（新华社）；忘还款影响征信 |

## 3.3 痛点强度总表（★为强度）

| 痛点 | 证据 | 强度 |
|---|---|---|
| 催款社交成本 | 朋友圈一手调研：26工管-aq **无引导自发提出**"自动向朋友发起 AA 收款、救救催款社恐"——用户呼声最高的功能点；LendingTree：38% 收到拆单请求的人觉得至少一次"不公平" | ★★★★★ |
| 高频小额转账 | AA 聚餐、拼单、社团经费、室友代付是该人群最高频资金行为（调研报告 4.1） | ★★★★ |
| 转错人灾难 | 微信手机号转账转错**不支持撤销**，协商无果只能法律途径（我苏网报道） | ★★★★ |
| 电诈高危 | 18-35 岁占电诈受害者 65.5%；16-35 岁占 45.86% 居各年龄段之首（湖北 2025）；高校案例：大二学生刷单被骗 3500 元 | ★★★★★ |
| 周期事务遗忘 | Gen Z 近 1/4 会忘账单到期日，53% 过去一年至少逾期一次（InvoiceCloud）；目标具体提醒可提升储蓄执行 16%（Decision Lab） | ★★★★ |
| 事后争议无凭证 | 押金纠纷是租赁投诉高发类型（v2.3：删除无出处的 33.3% 具体数字）；"这是赠与还是借款"的混合账本争议（调研 5.2） | ★★★★ |
| 群收款规则后置 | 微信群收款 30 天失效、停止收款不自动退款、催款靠手动截图——规则没提前说引发"不公平"感 | ★★★ |

## 3.4 需求优先级（调研结论 = 开发排序）

1. **低尴尬 AA 与系统代催** 2. **转账前强确认与延时纠错窗口** 3. **周期事务自动化** 4. **凭证化备注与电子回执** 5. **跨平台/非好友收款** 6. **隐私可控与关系账本**

## 3.5 人物画像（转账视角，与理财场景同一批角色）

**Persona 1 · 小知｜20 岁，大二**（月生活费 1600，住宿舍）
- 转账日常：宿舍拼单、班级聚餐 AA、给室友代付；单笔 5-200 元，对象固定
- 痛点：垫付 288 元聚餐费后不好意思催；月末对不上"谁还欠我钱"
- 与鹅豆的一天：聚餐后一句"6 人 288 帮我 AA 收一下"→ 规则确认后发出 → 24h 后鹅豆私聊代催 → 收齐；深夜被"刷单兼职"诱导转保证金时被鹅豆拦下
- 最常用：AA 全托管、小额快转、防骗雷达

**Persona 2 · 阿澈｜22 岁，大四，实习中**
- 转账日常：给房东转押金 2000、实习垫付交通费待报销、毕业旅行 AA、收到"培训贷"骚扰
- 痛点：给陌生房东转大额怕转错怕赖账；"这是借款还是赠与"说不清的混合账本
- 与鹅豆的一天：转押金触发新收款人升级确认+户名核验+默认延迟到账+电子回执归档进"租住"文件夹；垫付标记"待报销"，到账自动核销
- 最常用：强确认卡、凭证化备注、电子回执

**Persona 3 · 栗子｜24 岁，入职 8 个月**
- 转账日常：每月 5 号房租 1800、10 号还花呗、合租水电 AA（3 人长期）、同事婚礼随礼
- 痛点：工资日/还款日/房租日错开怕余额不足；随礼金额没谱；水电费每月算一遍
- 与鹅豆的一天：资金日历同历呈现三个日子；扣款前 3 天提醒"余额够，放心"；水电账单拍照进来 3 人长期 AA 自动结算；随礼时提示"上月现金流与同侪区间"
- 最常用：周期资金日历、Running AA、回执归档

# 第四部分 · 竞品启示：行业格局与我们的取舍

（详见《智能转账场景国内外银行业务调研》，此处留结论）

| 子场景 | 国内银行 | 国外银行 | 我们的取舍 |
|---|---|---|---|
| 手机号转账 | 人行"手机号码支付"跨行通道 + 各行 App | Zelle（2200+ 机构）、PayNow、UPI、Pix | 基础设施复用，差异化做**户名核验式确认**（v2.1：从"反查回显"升级为核验式，防枚举滥用） |
| 人名/昵称转账 | 行内通讯录为主，昵称空白 | Venmo 用户名、Zelle tag、Monzo 蓝牙 Nearby | 别名 + 消歧对话是 Agent 天然强项 |
| 备注转账 | 仅附言，无语义识别 | 同左（**全行业空白**） | ⭐备注语义化：模板 + 关联周期计划 + 喂账单 |
| 定时转账 | 成熟（单次/日/周/月/年） | standing order，规则简单；**条件触发无人做** | ⭐条件触发（工资到账后自动分配）+ 资金日历 |
| AA 收款 | **银行侧基本空白**，微信/支付宝群收款垄断 | **Monzo Split**（均分/比例/份额 + Running Split 净额结算 + 自动 nudging）、Revolut Group Bills、NatWest 标配 | ⭐⭐ 对标 Monzo Split，做"对话式发起 + 阶梯代催" |

**真正的对手是微信群收款**——答辩必须回答"微信已有群收款，你们做什么"（见第十部分应答话术）。

**四个行业空位（独创叙事）**：
1. **规则前置 AA**：国内外拆单工具都是"先算好再收款"，没人把"参与者先确认规则"做成流程一环
2. **语气化阶梯代催**：Monzo 有 nudging 但无人格；我们把催收语气做成 Agent 的核心能力（先私聊后提醒卡片、只 @ 未付者，且 Agent 不入群）
3. **备注语义化**："6月房租"自动关联周期计划——全行业空白
4. **条件触发定时**：工资到账后自动分配——全行业空白（理财场景的发薪日划转与此联动）

**对标基线**：与理财场景一致——微众 AI 强在中后台，C 端体验智能化是机会空位。

# 第五部分 · 产品方案

## 5.1 核心定位

**转账是高频入口场景，理财是价值深化场景**——转账负责"每天用"（活跃度），理财负责"把钱留下"（资产沉淀）。两者共用财富鹅人格、共用护栏层架构、共用留痕体系；转账数据（备注分类、AA 关系账本）暗线喂给账单分析场景——**该场景文档已建成（《账单分析场景·设计文档》v1.7，BA-B04 非标交易处理与本场景 memo_template/category 两层标签结构对接，v2.3 修订 F6：叙事不再指向不存在的文档）**，构成跨场景联动主线的一环。

## 5.2 三条体验红线（本场景专属，不可妥协）

| 红线 | 含义 |
|---|---|
| ① **AI 不静默执行** | AI 可识别、预填、推荐，但最终资金划转必须用户主动确认——任何字段（姓名/金额/备注/规则）由 AI 生成时须标识来源、可修改（T-R2） |
| ② **关系优先于效率** | 默认保护关系：金额不公开、催款先私聊后提醒卡片、未付名单仅发起人可见——透明服务于对账，不服务于羞辱 |
| ③ **小钱可选后悔，大钱必留窗口** | 已到账资金不可单方撤回（支付铁律）；熟人小额可选「可撤销转账」（延迟 2h 到账、窗口内可撤销）；新收款人/大额默认延迟到账，确认分级矩阵（TF-T09）是硬护栏。**命名说明（v2.3，外部挑刺 B2）**：原名"放心转"有体验悖论（放心的是付款人、收款人反而焦虑），更名「可撤销转账」如实描述功能；且**熟人小额默认即时到账，延迟档只在用户主动选择时出现**，不进默认推荐位 |

## 5.3 功能支柱详设

### 支柱 1：找对人（按人名 / 按手机号）

行为链（按人名）：
1. **联系人解析**："给张伟转 50 饭钱" → 命中 3 个"张伟"
2. **歧义追问卡片**："哪个张伟？篮球队的张伟（上次转账 3 月前）还是室友张伟（上周转过）？"——历史对象优先排序
3. **逐字回读**："收款人：张\*伟，尾号 6688，50 元，备注'饭钱'。对吗？"
4. **分级确认路由**（TF-T09 矩阵）→ 执行 → 回执

行为链（按手机号）：
1. 号码格式校验 → 2. **户名核验式确认**（v2.1 修订：掩码回显"该号码登记人：李\*明"；v2.3 修订：**姓氏补全为可选加强**——知道则核验加强，不知道走升级确认通道，不卡死；同设备枚举频次限制，防"批量查姓名"滥用）→ 3. 新收款人升级确认 + **默认延迟到账** → 4. 可一键存为联系人
- 换绑风险提示：手机号近期换绑后收款 = 账户接管高危信号（红线场景）

**关系分层**（调研 4.1）：好友/同学快转；新同事/房东默认延时到账；陌生人风控+凭证。分层由用户标注 + 行为推断（可改）。
> **双字段分工（v2.1 明确）**：`is_new`（是否有过成功转账记录）是**硬护栏字段**，决定确认强度与默认结算方式；`relation_level`（好友/房东/陌生人）是**软分层字段**，只决定话术语气与延时建议默认值——关系标错不会降低安全强度，标"好友"的新收款人照样走新收款人流程。

### 支柱 2：AA 全托管 ⭐创新主点

行为链：
1. **规则前置**：先定分摊方式（人均/按项目/有人免付/含服务费）→ 规则发参与者确认 → 确认后生成应收
2. **自然语言改算**："我不喝酒少算我点" → Agent 重算（你 28，其他五人 52）→ 回显确认
3. **跨平台发出**：逐个发出（同 App 用户）或生成**收款信息卡片+链接页**（v2.1 修订：链接页仅展示脱敏收款信息——金额、事由、收款人掩码，**支付在付款方自己的银行/支付 App 内完成**，我们不提供支付通道）
4. **阶梯代催**（状态机见 6.3 TF-T07）：24h 私聊轻松提醒 → 48h 再提醒 → 72h 生成提醒卡片由发起人**一键转发微信群**（Agent 不入群）
5. **收齐汇总**："288 收齐，本月你发起 AA 共收回 620" → 关系账本归档；逾期未付转入关系账本记录，不公开羞辱

> **支付状态口径（v2.3 修订，外部挑刺 A3——诚实分界）**：代催状态机的"已付/未付"分通道获得——**同 App（微众账户间）：转账回调自动追踪，状态精确**；**跨平台（钱进发起人的微信/支付宝/他行账户）：无支付结果回调，我们不假装知道**——付款方在链接页点"我已支付"→ 发起人收到核对通知并确认勾销（或直接手动核销），属**弱确认**而非支付通道回调。TF-T07 对跨平台未确认项的代催措辞相应降级（"小知还在等你确认哦"），并在产品内明示该限制——宁可收缩承诺，不留断点。

**演示金句**：*"把催款的社交压力转移给 Agent。"*

### 支柱 3：周期资金日历

行为链：
1. **一句话建规则**："每月 5 号给房东转 1200 房租" → 规则创建（任务级凭证，可改可停）
2. **资金日历**：工资日/还款日/房租日同历呈现——转账场景与理财场景共用的时间轴
3. **执行前校验**：扣款前 3-5 天余额检查，不足提前提醒改期（**不做自动垫付**——无信贷红线）
4. **失败即停**：一次扣款失败即停止并提示，不自动重试（T-R5 幂等控制）
5. **执行后回执**：电子回执自动归档（押金/房租/报销的辅助举证）
   > **回执效力定位（v2.3，外部挑刺 B5）**：回执是"带凭证号与时间戳的电子记录，证明某时某刻发生过某笔指令"，**不替代银行流水/司法凭证**，与关系账本"不构成法律凭证"同一效力层级——措辞统一为"辅助举证"，不用"举证链"强暗示
6. **条件触发**（增强）："工资到账后自动转 2000 进储蓄"——全行业空白，与理财场景发薪日划转联动

### 两个辅助能力
- **备注语义化**：八类模板（聚餐 AA/房租/押金/借款/还款/随礼/班费/公费），AI 摘要 + "AI 建议"标识 + 分类标签喂账单；"每月 5 号那笔 1200 是房租" → 自动建议关联周期计划
  - **"借款"模板边界（v2.3，外部挑刺 B4）**：仅为**用户自发的备注分类**——平台不催收、不计息、不生成借条、不提供任何借贷撮合；关系账本"未还借款"系用户自记，平台不介入追偿（与"不构成法律凭证"声明一致）；不做信贷的承诺不因一个备注标签而破功
- **跨平台收款卡片**：对方无需同 App——收款信息卡片/链接页展示脱敏收款信息，支付在对方自己的 App 完成（v2.1 明确：**我们不碰收单业务、不发支付通道、不碰信用卡**，无需收单资质；防钓鱼链接设计——链接域名固定+卡片内嵌防伪标识）

### 明确不做（边界声明）
- ❌ 平台沉淀资金（不做资金池；AA 资金由持牌通道直连收款人账户，平台不触碰——"防二清"防的是平台截留，不是"资金不落地"，v2.3 口径修订 B6）
- ❌ 收单/支付通道业务（跨平台收款仅提供脱敏信息卡片，支付在对方 App 完成）
- ❌ 向不特定对象发起收款（AA 限定熟人邀请制）
- ❌ 经营性收款（个人 AA 不作商用码替代）
- ❌ 任何信贷/垫付形态（余额不足只提醒改期）
- ❌ 公开账单 feed（Venmo 式社交曝光是隐私红线）
- ❌ AI 免密执行（任何场景）
- ❌ Agent 直接进入微信群（代催通过"提醒卡片由发起人转发"实现）

### TF-T01 按人名转账（多步规划主展示，评审 40%）

```
用户: "给张伟转50饭钱"
  │
  ├─ Step1 [工具] contact.resolve("张伟") → 命中3人

  ├─ Step3 [注入隔离] 备注"饭钱"走 TF-T03 模板匹配（餐饮类）
  ├─ Step4 LLM 逐字回读: "收款人：张*伟，尾号6688，50元，备注'饭钱'。对吗？"

```

要点：任一步用户改口（"是篮球队那个"）→ 回 Step2 重选而不是重来（错误恢复）。

  │                  （防"批量跑号码查姓名"——反查功能不得成为信息泄露口）
  │         [硬护栏] 号码近期换绑? → 风险提示升级（账户接管信号）

  ├─ [硬护栏] 新收款人 → TF-T09 升级确认（TOTP/密码）+ 默认延迟到账（窗口内可撤销）

### TF-T03 备注语义化（v2.1：敏感词加模板白名单）

```
伴随所有转账意图:

  ├─ [硬护栏] 敏感信息过滤（密码/验证码/身份证号/卡号 → 拦截并提示）
  ├─ [硬护栏] 敏感词过滤（"保证金/刷单/解冻费/跑分"）——两档处置:
  │    ├─ 模板化备注命中（如选"押金"模板、备注含"押金"）→ 白名单豁免，

### TF-T07 阶梯代催（状态机；v2.1：双通道，Agent 不入群）

```
状态: UNPAID → REMINDED_1 → REMINDED_2 → CARD_READY → (PAID | LEDGER)

T+24h: 私聊付款人（轻松档）: "嗨，昨晚聚餐的52块，小知在等哦～"
       通道: 微众用户 → App 内消息；非微众用户 → 短信/收款卡片链接页提醒
T+48h: 私聊（正式档）: "聚餐AA还差你这笔，方便的话今天转一下？"
T+72h: 通知发起人: "还有2位没付，要我生成提醒卡片吗？（只列未付的两位）"
       → 发起人确认 → [工具] aa.remind_card 生成提醒卡片
       → 发起人一键转发到微信群（Agent 不入群、不代发群消息）
       卡片内容: 事由+人均金额，只@未付者，不公开各人明细
收齐: "288收齐了。本月你发起AA共收回620。"

### TF-T08 防骗雷达（状态机，评审 30% 主演示）

```
信号采集（对话全程运行）:
  硬信号（规则代码）: 新收款人 / 夜间(23-6) / 大额 / 敏感词命中("保证金""安全账户""刷单""解冻费")
  软信号（LLM）: 急迫话术、冒充客服/公检法语义 → 风险分 0-100

风险分级与处置:
  低（单一弱信号）→ 常规确认，无打扰
  中（硬信号≥2 或 软信号>60）→ 风险提示朗读 + 强确认
       "这笔转账有几个异常信号：新收款人+深夜。请再确认一次。"
  高（敏感词+新收款人 或 软信号>85）→ TF-T08 完整处置:
       ① 风险警告朗读（点破话术套路: "这是典型的兼职刷单诈骗话术——先给小额返利，
          再以'保证金/解冻费'要大钱。全国每年大量同学因此被骗。"）
       ② TOTP 二次验证
       ③ 延迟到账选项（默认推荐 24h，窗口内可撤销）
       ④ [留痕] scam_signals 记录
       ⑤ 用户坚持 → 强确认 + 标记"用户已确认坚持"（交易自主权，T-R8）
       ⑥ 误伤救济: "这是正常转账" → 二次验证后放行并降低该收款人风险分
```

### TF-T09 确认分级路由（阈值矩阵；v2.1：新增"结算方式"列）

| 条件 | 确认强度 | 结算方式（v2.1） |
|---|---|---|
| 熟人 + ≤50 元 | 逐字回读 + 一句话确认 | 默认**即时到账**；可选「可撤销转账」（延迟 2h，窗口内可撤销） |
| 熟人 + 50~200 | 回读 + 确认 | 默认即时到账；可选「可撤销转账」 |
| **新收款人** 或 >200 | 户名核验 + TOTP/密码 | **默认延迟到账（2h）**，窗口内可撤销 |
| >1000（示例阈值，沙箱可调） | 升级确认 + 金额大写复读 | **默认延迟到账（24h 选项）**，窗口内可撤销 |
| 新收款人 + 夜间(23-6) | 全部叠加 | 延迟到账强制开启，不可选即时 |
| 命中防骗雷达 | 叠加 TF-T08 处置 | 见上 |

> 阈值为示例值，按账户类别/验证强度/风险等级动态调整（T-R7）；演示用沙箱参数，答辩声明"真实展业由持牌机构风控定参"。
> **支付铁律（v2.1 声明）**：已结算到账的资金所有权已转移，任何机构无权单方撤回——我们撤销的永远是"窗口内尚未结算的指令"，不是"已到账的钱"。

### TF-T10 撤销与延时窗口（v2.1 重定性：撤销的是指令，不是资金）

```
前置认知（硬红线）: 已到账资金不可单方撤回——这是支付体系铁律，不是我们吝啬。

实现机制声明（v2.3，外部挑刺 F4——把底座讲实）:
  "延迟结算+窗口撤销"依托银行侧的预约转账/挂账能力，Agent 层只做指令编排：
  ├─ 微众行内转账: 复用行内预约/挂账能力，窗口内撤销可行（设计假设，标注待验证）
  ├─ 跨行/跨平台通道: 以各通道实际能力为准；不支持延迟结算的通道降级为
  │    "延迟确认"（指令暂缓发出）+ 客诉拦截流程，并在确认页如实告知
  │    "该通道不支持中途撤销"
  └─ 沙箱演示为模拟能力；答辩如实声明"真实展业由持牌机构通道提供"

可撤销场景 = 延迟结算窗口内的未执行指令:
  ├─ 「可撤销转账」（熟人小额可选）: 延迟 2h 到账
  │    → 窗口内"刚才那笔转错了" → [工具] transfer.cancel（指令撤销，资金未动）
  ├─ 新收款人/大额默认延迟到账（2h/24h）: 天然带撤销窗口
  │    → 窗口内发现被骗/转错 → 撤销 + 联动 TF-T08 留痕
  ├─ [硬护栏] 窗口外（已结算）→ 不可撤销，转入客诉/协商/司法流程
  │         （提供电子回执与对方脱敏信息作为举证支持）
  └─ [留痕] 撤销记录；对方侧收款通知标注"已撤销"
```

## 6.6 LLM 编排要点

- **System Prompt 结构**：鹅豆人格 → 能力边界（AI 不静默执行）→ 工具清单 → 护栏话术模板（消歧追问/回读/风险警告/代催模板）→ 当前用户状态注入（关系分层、常用收款人、进行中 AA、资金日历摘要）
- **不可信字段注入隔离**：TF-T12 全程生效
- **代催话术三档 + 一个终止动作**（v2.1 与 TF-T07 状态机口径统一）：轻松档（24h 私聊）/ 正式档（48h 私聊）/ 提醒卡片档（72h 发起人转发）+ 终止动作（7 天转关系账本不再催）——语气由模板控制，不让模型自由发挥（防语气翻车）
- **话术红线**：不得替用户承诺"对方一定会还"、不得在提醒卡片中公开各人金额明细、不得以用户名义在群内发言
- **依据句规范（设计纲领·纲领四，v2.2 新增）**：**话术三分层**——事实（流水/账户数据）/ 推断（分类、关系分层、风险评分）/ 建议（行动选项）在输出中可区分；一切风险提示必带**依据句**（"这笔转账有几个异常信号：新收款人+深夜"——逐条点名信号，不说"我觉得可疑"）；一切估算必标**推测成分**（"按近三月均值估算"）；不得把可能性包装成确定结论（官方原文红线）

# 第十部分 · 差异化对照与原创性声明

## 10.1 最大对手：微信群收款（答辩必答题）

| 维度 | 微信群收款 | 我们（鹅豆 AA 全托管） |
|---|---|---|
| 规则 | 发起时手算，**规则后置** | **规则前置**：参与者确认后才生成应收 |
| 催款 | 24h 系统提醒一次，之后靠手动截图/私信 | **阶梯代催**（24/48/72h 语气分级：先私聊双通道提醒，后由发起人一键转发提醒卡片，只 @ 未付者） |
| 改算 | 不支持非等额的自然语言调整 | "我不喝酒少算我 20"一句话重算 |
| 安全 | 无诈骗识别 | 防骗雷达 + 分级确认 + 延时窗口 + 注入隔离（银行级） |
| 留痕 | 30 天失效、停止收款不退款 | 电子回执 + 10 年留痕 + 关系账本（仅本人可见） |
| 身份 | 社交工具里的资金功能 | **银行里的关系功能**——资金不出银行体系，可信背书 |

**应答话术**："微信群收款解决了'能收'，我们解决'收得体面、收得安全、收得有凭证'——规则前置让事后**有据可查**（v2.3 修订 F5：参与者确认是流程留痕，不构成付款承诺，我们不再说'消灭争议'），阶梯代催把催款的社交压力转移给 Agent，银行级防骗与留痕是社交工具给不了的。"

## 10.2 其他相似源对照

| 风险源 | 相似点 | 我们的差异 | 结论 |
|---|---|---|---|
| Monzo Split / Revolut | 拆单+自动催款 | 对话式发起、规则前置、语气化代催（且 Agent 不入群）；且我们是国内银行语境（它们进不来） | 模式借鉴，**低** |
| Zelle Request | 收款请求模式 | 同上；Request 模式本身是行业通行设计 | **低** |
| Splitwise | 关系账本 | 它只记账不动钱；我们资金+账本一体且默认私密、可删除 | **低** |
| 支付宝 AA 收款 | 功能同名 | 同微信群收款对照逻辑 | **低** |

## 10.3 原创性声明（可放答辩 PPT）

> 本模块的基础能力（手机号转账、定时转账、拆单收款）均为行业通用模式，我们引用人行手机号码支付、Zelle、Monzo Split、Revolut、微信群收款等国内外公开实践作为多源佐证；全部交互形态、话术、代码为本团队原创。四个组合点——规则前置 AA、语气化阶梯代催（Agent 不入群）、备注语义化、条件触发定时——经调研确认尚无同业实践，为本方案独创。涉及支付结算的设计遵守"已结算资金不可单方撤回"铁律，撤销能力仅作用于延迟结算窗口内的未执行指令。
