# 知行语音银行两项核心技术应用研究

## ——微众银行联邦学习与证据驱动的多 Agent 辩论

> 研究日期：2026-10-24  
> 研究对象：账单分析、智能转账、理财操作、卡片管理、订阅代扣管理、跨场景联动  
> 结论性质：技术选型与验证方案，不代表已接入真实银行数据或真实机构联邦

# 执行摘要

**建议把两项技术做成两条互补、但可以独立成立的主线，而不是六个场景平均堆砌。**第一条是“联邦风险识别”：针对单家银行诈骗样本类型有限、原始交易数据又不能集中共享的矛盾，在转账事前风险提示和账单事后异常复核中使用横向跨机构联邦学习。第二条是“证据驱动的多 Agent 辩论”：针对单 Agent 在复杂任务链中容易漏看反例、授权和副作用的问题，在跨场景规划、异常交易复核和存在冲突的订阅路由中，引入独立初答、交叉质询和证据裁决。两者都不直接决定转账、申购、挂失或退订，最终执行仍由确定性规则、机构回执、强认证和用户确认控制。

这两个亮点与比赛要求存在真实对应关系。联邦学习体现微众银行技术脉络下的隐私协作与跨机构模型能力，多 Agent 辩论体现任务规划、结果解释、安全合规和错误恢复，但成立的前提是可测量地优于简单基线。如果联邦模型不能在各参与机构本地测试集上超越本地模型，或辩论不能降低关键遗漏与无依据断言，就不应为了展示而上线。最小可行版本只需完成“三方合成数据联邦实验”和“三 Agent、最多两轮、只读证据包”的验证，不应声称已经连接其他银行或形成真实行业网络。

# 一、技术理论及其真正解决的问题

## 1.1 联邦学习：数据协作不等于数据集中

联邦学习的基本目标是让多个参与方在本地保存数据并训练模型，再通过受保护的模型更新协作形成全局或个性化模型。横向联邦中，各参与方的用户群可以不同，但特征空间相近；纵向联邦中，各参与方持有同一批重叠样本的不同特征，通常需要隐私求交、标签方以及协同预测。FATE 官方文档对纵向 SecureBoost 的描述也明确了共同样本、不同特征、隐私对齐和加密训练这些前提，因此不能仅因为“有两个系统”就宣称适合纵向联邦。[FATE 官方教程](kimi-cite://web?url=https%3A%2F%2Fgithub.com%2FFederatedAI%2FFATE%2Fblob%2Fmaster%2Fdoc%2F2.0%2Ffate%2Fml%2Fhetero_secureboost_tutorial.md "citation")

横向联邦最常见的 FedAvg 可写为：

\[
w_{t+1}=\sum_{k=1}^{K}\frac{n_k}{\sum_{j=1}^{K}n_j}\,w_{t+1}^{k}
\]

其中，第 \(k\) 个参与方在本地数据上得到更新 \(w_{t+1}^{k}\)，聚合方按样本量或其他经过治理的权重形成新模型。这个公式只说明参数如何组合，并不自动保证公平、收敛或隐私。不同银行的诈骗类型、客户结构和标签质量通常是非独立同分布的，简单平均可能让大机构主导全局模型，也可能损害小机构本地表现，所以必须比较 FedAvg、个性化或鲁棒聚合，并保留本地模型兜底。非 IID 数据对联邦优化的影响已有长期研究，不能将联邦训练等同于必然优于本地训练。[非 IID 联邦学习研究](kimi-cite://web?url=https%3A%2F%2Farxiv.org%2Fhtml%2F1806.00582v2 "citation")

| 形态 | 数据关系 | 本项目适配 | 不应误解为 |
|---|---|---|---|
| 横向跨机构联邦 | 不同机构、不同用户，特征口径相近 | **适合**：跨机构诈骗与异常模式识别 | 共享对方流水、黑名单或客户身份 |
| 纵向联邦 | 共同样本、不同机构特征，需要隐私求交 | 暂不首发：当前没有真实共同样本和合作方 | 两个系统简单拼接字段 |
| 跨设备联邦 | 大量终端本地训练、掉线与异构显著 | 不作为比赛主线：端侧标签与成本条件不足 | 在每个用户手机训练就必然更隐私 |
| 联邦统计／安全聚合 | 只计算统计量，不训练预测模型 | 同龄分位应走这一方向，而非联邦学习 | 为了使用 FATE 把简单统计变成训练任务 |

## 1.2 隐私保护需要完整威胁模型

“原始数据不出域”只消除了集中原始数据库这一条风险路径，并未消除模型更新泄露、成员推断、梯度反演、恶意参与方投毒、 aggregator 操纵和全局模型后门。近期联邦安全研究仍把这些攻击列为核心问题，因此项目的隐私叙事必须从一句口号升级为可检查的机制：参与方认证、最小特征、更新裁剪、安全聚合、差分隐私预算、鲁棒聚合、模型签名、版本审计和快速回滚。[联邦学习安全与隐私综述](kimi-cite://web?url=https%3A%2F%2Farxiv.org%2Fhtml%2F2508.13730v1 "citation")

合规边界同样需要单独判断。金融账户属于敏感个人信息，自动化决策需要透明、公平和必要的说明，重大影响决定不能只依赖自动化流程；银行保险机构的模型还应可验证、可审核、可追溯，并具备风险缓释和退出 AI 的替代方案。联邦学习只是技术保护措施之一，不能替代处理目的、必要性、授权、影响评估和机构间责任约定。[个人信息保护法](kimi-cite://web?url=https%3A%2F%2Fwww.cac.gov.cn%2F2021-08%2F20%2Fc_1631050028355286.htm "citation") [银行保险机构数据安全管理办法](kimi-cite://web?url=https%3A%2F%2Fwww.nfra.gov.cn%2Fcn%2Fview%2Fpages%2FgovernmentDetail.html%3FdocId%3D1192311%26itemId%3D861%26generaltype%3D1 "citation")

## 1.3 多 Agent 辩论：分歧用于找错，不用于表决资金动作

多 Agent 辩论让多个模型实例先独立作答，再阅读彼此观点、提出批评并修订，经过有限轮次后形成裁决。原始研究展示了它在部分数学推理和事实任务上的潜力，其关键并非“三个角色一起聊天”，而是初始推理路径的独立性、对其他答案的实质检查，以及根据批评进行修正。若一开始所有 Agent 都看到同一个答案，或只有角色名称不同而没有独立证据和反例，往往只是成本更高的流水线。[多 Agent 辩论原始论文](kimi-cite://web?url=https%3A%2F%2Farxiv.org%2Fpdf%2F2305.14325 "citation")

在本项目中，辩论对象应是结构化的“主张—证据—反例—建议动作”，而不是自由发挥的长篇对话。每个主张必须引用证据编号，例如 `RULE_NEW_PAYEE`、`USER_CONFIRMED_MERCHANT`、`BANK_PROTOCOL_STATUS` 或 `FED_MODEL_V12`。裁决器可以不选任何一方，输出“证据不足”“需要用户补充”或“转人工复核”。多数一致只能表示观点一致，不能证明商户身份、诈骗事实、合同状态或用户授权。

| 组成 | 合理做法 | 不合理做法 |
|---|---|---|
| 独立初答 | 不同角色只读取最小证据包，独立提出计划与反例 | 所有 Agent 复制同一上下文和结论 |
| 交叉质询 | 最多两轮，必须指出缺失证据或规则冲突 | 无限制讨论、互相客套或为了共识而共识 |
| 裁决 | 证据强度、规则校验、可逆性和用户权利优先 | 多数票、自信分数或表达能力决定执行 |
| 工具权限 | 只读检索和规则验证，写工具不开放 | 辩论 Agent 直接转账、申购、挂失或退订 |
| 留痕 | 保存证据、主张、分歧、裁决和版本 | 把隐藏思维链当成合规解释或事实来源 |

## 1.4 辩论也会制造一致的错误

后续研究发现，多 Agent 辩论并不稳定优于单 Agent，较强 Agent 可能被较弱但自信的观点说服，正确答案也可能在讨论中已经被提出却被多数忽略。这被称为迎合、过早收敛或多样性塌缩。由此，项目不应把“共识率”当成准确率，反而要跟踪正确立场被放弃、无新证据改口和一致但错误的比例。[辩论失效模式研究](kimi-cite://web?url=https%3A%2F%2Farxiv.org%2Fhtml%2F2509.05396v1 "citation") [共识成本研究](kimi-cite://web?url=https%3A%2F%2Faclanthology.org%2F2025.findings-acl.1141.pdf "citation")

多 Agent 还会增加提示注入、数据外泄、工具权限和级联故障的攻击面。一个被恶意商户文本影响的 Agent，可能把污染内容传播给其他 Agent。OWASP 对 Agent 安全的建议也覆盖提示注入、工具滥用、过度自治和多 Agent 级联失败。因此证据包需清洗并标记不可信文本，Agent 之间只传结构化主张，不传可执行指令；超时、服务不可用或争议未解时，退回单 Agent 只读建议或人工流程。[OWASP Agent 安全指南](kimi-cite://web?url=https%3A%2F%2Fcheatsheetseries.owasp.org%2Fcheatsheets%2FAI_Agent_Security_Cheat_Sheet.html "citation")

# 二、六个场景的痛点映射与取舍

项目现有设计已经具备确定性硬护栏、授权确认和机构回执边界。两项技术应补的是“样本不足”和“复杂推理漏检”，而不是重写这些基础。转账已有新收款人、夜间、大额和敏感语义等信号，账单已有个人基线与事后复核，跨场景已有 `link_chain` 和确认节点，这些恰好分别提供了联邦特征、个人反证和辩论对象。[智能转账场景·设计文档](kimi-cite://md-line?path=C%3A%5CUsers%5CSurface%5CDesktop%5C%E5%BE%AE%E4%BC%97%E9%87%91%E8%9E%8D%E7%A7%91%E6%8A%80%E5%A4%A7%E8%B5%9B%5C%E6%99%BA%E8%83%BD%E8%BD%AC%E8%B4%A6%E5%9C%BA%E6%99%AF%5C%E6%99%BA%E8%83%BD%E8%BD%AC%E8%B4%A6%E5%9C%BA%E6%99%AF%C2%B7%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3.md&line=407&text=%23%23%23%20TF-T08%20%E9%98%B2%E9%AA%97%E9%9B%B7%E8%BE%BE%EF%BC%88%E7%8A%B6%E6%80%81%E6%9C%BA%EF%BC%8C%E8%AF%84%E5%AE%A1%2030%25%20%E4%B8%BB%E6%BC%94%E7%A4%BA%EF%BC%89 "citation") [跨场景联动场景设计文档](kimi-cite://md-line?path=C%3A%5CUsers%5CSurface%5CDesktop%5C%E5%BE%AE%E4%BC%97%E9%87%91%E8%9E%8D%E7%A7%91%E6%8A%80%E5%A4%A7%E8%B5%9B%5C%E8%B7%A8%E5%9C%BA%E6%99%AF%E8%81%94%E5%8A%A8%E5%9C%BA%E6%99%AF%5C%E8%B7%A8%E5%9C%BA%E6%99%AF%E8%81%94%E5%8A%A8%E5%9C%BA%E6%99%AF%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3.md&line=112&text=%23%23%205.1%20%E7%BB%9F%E4%B8%80%E8%81%94%E5%8A%A8%E5%8D%8F%E8%AE%AE%EF%BC%88%E5%85%A8%E5%9C%BA%E6%99%AF%E7%9A%84%E4%B8%80%E7%AD%89%E5%85%AC%E6%B0%91%EF%BC%89 "citation")

**优先级不是按技术展示效果排列，而是按“痛点强度 × 不可替代性 × 可验证性 × 风险”排列。**转账和账单最适合联邦学习，跨场景最适合辩论；订阅可共享同一风险证据和辩论协议，但不应为了覆盖六场景而扩张。理财和卡片主要采用受限辅助，避免把技术变成自动授信或自动解控。

| 场景 | 真实痛点 | 联邦学习是否必要 | 多 Agent 辩论是否必要 | 推荐定位 |
|---|---|---|---|---|
| 智能转账 | 单机构见到的诈骗类型有限，新骗局跨机构传播；硬规则对新模式覆盖不足 | **高**：不同机构、相似交易特征、可积累确认标签 | 低—中：只对语义冲突做只读复核，不进入放行表决 | **联邦首发**，辩论谨慎辅助 |
| 账单分析 | 个人冷启动、异常与正常行为相似、单一模型容易把信号当事实 | **高**：共享跨机构异常模式，本地保留个人基线 | **高**：联邦信号、个人节律和用户说明可能互相冲突 | **两项技术汇合的旗舰场景** |
| 跨场景联动 | 多步骤任务容易漏掉授权、顺序、数据最小化或不可逆副作用 | 无必要：不是跨机构训练问题 | **高**：独立规划、反例和消保审查确实能降低关键遗漏 | **辩论首发** |
| 订阅代扣 | 商户别名与周期识别需要多样样本；商户、银行和通道状态容易混同 | 中：第二阶段做商户归一化和订阅分类 | 中：只在身份或路由冲突时辩论 | 复用能力，不直接判断退订成功 |
| 理财操作 | 产品说明复杂、风险揭示可能遗漏；适当性是规则而非讨论题 | 低：不用于风险等级或购买许可 | 中：用于客观比较与风险揭示审查 | 限定为只读说明审查 |
| 卡片管理 | 风控误伤后解释不清；审批、解锁和司法程序边界严格 | 中—低：远期可研究跨机构误伤模式，不进入 MVP | 低：不参与审批、解冻或司法判断 | 只审查解释与材料完整性 |

# 三、亮点一：联邦风险识别网络

## 3.1 首发问题：转账与账单共享模型，不共享原始流水

转账侧重“钱尚未出去”的事前风险提示，账单侧重“钱已经出去”的事后复核与止损指引，两者可以复用同一联邦风险模型的不同证据视图。参与机构分别保留本地交易、收款人关系和用户确认结果，只用统一 Schema 提取必要特征，如金额区间、时间窗口、新收款人、短期频次、商户类别、历史关系强度和已核实风险类型。原始账号、姓名、卡号、完整备注、精确时间和地点不进入联邦特征包。模型输出包括风险分、可披露原因类别、模型版本和适用范围，不输出其他机构客户信息。

标签质量比模型复杂度更重要。建议只把机构确认诈骗、用户确认本人正常交易、争议处理结论等作为训练标签；单纯“深夜”“新商户”“用户忽略提醒”不能当作诈骗标签，未知样本应排除或单独处理。联邦模型学习群体风险模式，个人基线仍留在本地判断“这是否像本人”。这样可以避免把年轻人的夜间消费、异地求职或新商户消费直接标签化为高风险，也能缓解单一机构新型诈骗样本不足的问题。

## 3.2 FATE 采用方式与运行边界

比赛原型可采用 FATE 横向联邦或与其等价的本地多进程模拟，设置三个合成机构节点，各自拥有不同诈骗类型分布和非 IID 正常交易。训练阶段执行本地训练、受保护聚合、全局评估和版本发布；推理阶段只在本地读取已签名模型，不要求每笔交易跨机构在线通信。这个区分很重要：联邦训练可以是离线或准离线的，支付主链路不应因为其他机构节点不可用而停摆。

全局模型不是银行风控的替代品。它只向现有 `scam_signals` 增加一项 `federated_risk_evidence`，由本地确定性策略决定提醒、增强验证或人工复核；用户坚持、机构限额和正式处置仍按原有流程。联邦服务故障时退回本地模型和硬规则，模型表现漂移时回滚版本。任何演示都必须写明“合成机构、合成数据、模拟联邦”，不能把三方模拟描述为微众银行已与外部机构建立数据合作。

## 3.3 为什么它能切实改善现有痛点

现有硬规则擅长识别已知组合，却很难覆盖单机构从未见过的新型诈骗；单纯 LLM 又能理解话术，却可能把语言相似性当成事实。联邦模型补的是跨机构样本覆盖，LLM 只负责解释可披露信号，两者职责不同。近期跨机构支付反诈研究也把价值重点放在不同机构 fraud typologies 的泛化，但其合成数据和诚实参与方假设意味着结果不能直接外推为生产收益，因此本项目不引用研究分数作为自身承诺。[跨机构联邦反诈概念验证](kimi-cite://web?url=https%3A%2F%2Farxiv.org%2Fhtml%2F2603.13617v1 "citation")

成功标准应设为“在相同误报约束下发现更多已确认风险，并且多数参与机构受益”，而非只提高总体准确率。建议对每个机构分别报告 PR-AUC、固定误报率下召回率、提醒精确率、未知骗局类型的召回和分群误报差异，同时记录通信轮次、训练耗时、隐私预算和投毒测试结果。如果联邦模型只让大机构受益，或小机构误报明显上升，应采用个性化聚合、调整参与权重，或停止上线。

# 四、亮点二：证据驱动的多 Agent 合规辩论

## 4.1 三类 Agent 不是 persona 表演，而是三种检查目标

任务规划 Agent 关注“怎样完成用户目标”，提出步骤、依赖和所需信息；证据质疑 Agent 关注“哪些假设可能为假”，主动寻找相反解释和缺失证据；消保合规 Agent 关注“即使能完成，是否应当这样完成”，检查授权、数据最小化、用户退出权、后果披露和人工渠道。三者目标不同，才可能产生有意义的反例。若只给同一模型分配“银行家、律师、用户”称呼，却仍要求快速达成一致，不构成可靠辩论。

裁决层不再是一个凭语言表达选答案的 LLM 裁判，而是“结构化裁决器＋确定性验证器”。结构化裁决器只整理无争议事实、仍存争议、需要补充的证据和建议路径；确定性验证器检查金额、权限、步骤状态、通道能力和禁止事项。最终向用户展示的是简明依据和选项，不展示角色争吵，也不把内部推理文本当作事实。

| Agent／组件 | 核心问题 | 典型输出 | 权限 |
|---|---|---|---|
| 任务规划 Agent | 如何以最少步骤完成目标 | 候选 DAG、所需字段、预期结果 | 只读规划 |
| 证据质疑 Agent | 哪个前提可能错误或过期 | 反例、缺失证据、替代解释 | 只读检索 |
| 消保合规 Agent | 是否越权、误导或损害退出权 | 授权冲突、后果遗漏、人工路径 | 只读规则检查 |
| 结构化裁决器 | 哪些事实一致，哪些仍不确定 | 证据清单、未决问题、候选方案 | 不执行 |
| 确定性验证器 | 当前状态能否进入下一确认节点 | 通过、拒绝、需补字段、需人工 | 硬校验 |
| 用户／机构 | 是否授权执行，是否通过正式风控 | 确认、拒绝、强认证、机构回执 | 最终决定 |

## 4.2 有界辩论协议

推荐协议为“三方独立初答→一轮交叉质询→必要时第二轮补证→结构化裁决→确定性验证”，默认最多两轮。初答阶段不互相可见，质询阶段匿名化 Agent 身份，要求每次改口说明新增证据。若争议只涉及表达而没有新事实，应提前停止；若出现证据冲突、规则冲突或高后果不可逆动作，则输出补充问题或人工复核，而不是继续投票。全程记录模型版本、证据版本、主张变化和停止原因。

每次辩论采用统一结构：

```json
{
  "claim": "建议先核对商户身份，再提供官方取消入口",
  "evidence_ids": ["MERCHANT_ALIAS_AMBIGUOUS", "BANK_STATUS_NOT_APPLICABLE"],
  "counterevidence_ids": ["USER_SAYS_ALREADY_CANCELLED"],
  "uncertainties": ["商户侧是否仍有效"],
  "proposed_action": "REQUEST_USER_CONFIRMATION",
  "forbidden_inference": "不得由银行通道状态推断商户合同状态"
}
```

这里的 JSON 只是接口示意，不代表真实回执。生产实现还应对证据类型、有效期、来源和权限做 Schema 校验，禁止 Agent 自创 `BANK_APPROVED`、`USER_CONFIRMED` 等高权限事实。外部商户文本、OCR 和网页内容只能作为不可信证据，不得包含可驱动工具的指令。

## 4.3 首发应用：跨场景规划与异常复核

跨场景规划中，任务规划 Agent 可能提出“预算预留→外部下单→账单标注”，证据质疑 Agent 检查预算罐是否可被第三方扣款、外部价格是否有依据、生日信息是否获得授权，消保合规 Agent 检查第三方字段传输和每一步确认。辩论的价值不是让生日方案更有创意，而是防止任务链在跨域时丢失原有边界，最终仍由 `link_chain` 和用户确认执行。

账单异常复核中，联邦模型可能给出高风险证据，个人基线却显示用户近期有相似消费，用户也可能已确认商户。规划 Agent 提议提醒，质疑 Agent 检查是否把“首次商户”误当“盗刷”，合规 Agent 保证只输出“疑似、待核实”和官方处置入口。订阅场景复用同一机制处理商户别名、用户已取消反馈和通道状态冲突，但商户退订、银行授权和实际未扣仍分别以回执与流水为事实，不能由辩论推断。[账单分析场景·设计文档](kimi-cite://md-line?path=C%3A%5CUsers%5CSurface%5CDesktop%5C%E5%BE%AE%E4%BC%97%E9%87%91%E8%9E%8D%E7%A7%91%E6%8A%80%E5%A4%A7%E8%B5%9B%5C%E8%B4%A6%E5%8D%95%E5%88%86%E6%9E%90%E5%9C%BA%E6%99%AF%5C%E8%B4%A6%E5%8D%95%E5%88%86%E6%9E%90%E5%9C%BA%E6%99%AF%C2%B7%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3.md&line=411&text=%23%23%23%20BA-B05%20%E5%BC%82%E5%B8%B8%E4%BA%A4%E6%98%93%E8%AF%86%E5%88%AB%EF%BC%88%E5%86%B7%E5%90%AF%E5%8A%A8%2B%E8%8A%82%E5%BE%8B%E7%99%BD%E5%90%8D%E5%8D%95%2B%E4%BA%8B%E5%90%8E%E5%A4%8D%E6%A0%B8%E5%AE%9A%E4%BD%8D%EF%BC%89 "citation") [订阅代扣管理场景设计文档](kimi-cite://md-line?path=C%3A%5CUsers%5CSurface%5CDesktop%5C%E5%BE%AE%E4%BC%97%E9%87%91%E8%9E%8D%E7%A7%91%E6%8A%80%E5%A4%A7%E8%B5%9B%5C%E8%AE%A2%E9%98%85%E4%BB%A3%E6%89%A3%E7%AE%A1%E7%90%86%E5%9C%BA%E6%99%AF%5C%E8%AE%A2%E9%98%85%E4%BB%A3%E6%89%A3%E7%AE%A1%E7%90%86%E5%9C%BA%E6%99%AF%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3.md&line=258&text=%23%23%205.3%20F3%20%E4%B8%80%E9%94%AE%E8%A7%A3%E7%BA%A6%EF%BC%88%E4%B8%89%E5%B1%82%E8%83%BD%E5%8A%9B%EF%BC%89%E2%80%94%E2%80%94%E6%9C%AC%E5%9C%BA%E6%99%AF%E7%9A%84%E6%89%A7%E8%A1%8C%E6%A0%B8%E5%BF%83 "citation")

# 五、两项技术如何形成组合亮点

## 5.1 组合不是串联炫技，而是“证据生产—证据质疑”

联邦学习负责从多方样本中产生风险证据，多 Agent 辩论负责检查该证据在当前用户和当前任务中是否足以支持建议。前者可以回答“这类模式在多方样本中是否异常”，后者必须继续问“是否适用于这个人、是否与用户确认冲突、是否越权”。这样能够避免两种常见幻觉：把联邦风险分当作诈骗事实，以及把多个 Agent 的一致意见当作银行决定。

推荐旗舰案例是一笔存在冲突证据的账单异常，而不是简单转账。系统先展示本地硬信号、个人基线和联邦模型版本化证据，再由 Agent 争论“异常消费还是用户新生活方式”。最后输出“高优先级待核实”或“证据不足，不主动打扰”，并提供本人确认、非本人挂失和申诉路径。该案例同时体现跨机构学习、个人差异、证据裁决和消费者保护，且不需要让 AI 真的执行资金动作。

## 5.2 答辩展示应当呈现可验证过程

联邦部分展示三方合成机构的不同诈骗分布、本地模型与联邦模型的同测试集对比，以及安全聚合、隐私预算和模型回滚记录。辩论部分展示三方独立初答确实不同、质疑方指出了哪个具体缺证、裁决如何保留不确定性，以及确定性护栏如何阻止越权动作。评委看到的应是“为什么值得用”和“如何防止用错”，而不是动画里的多个头像互相说话。

可用一句答辩话术概括：**“联邦学习让风险模型看见单机构看不见的样本，但不看见彼此的客户；多 Agent 辩论让计划接受反例审查，但任何 Agent 都不能替用户和银行做决定。”**这句话同时说明收益、边界和架构，不应再附加“零泄露”“消除幻觉”“全自动风控”等无法证明的承诺。

# 六、验证方案与比赛验收指标

## 6.1 必须设置简单基线和失败退出条件

联邦实验至少比较本地模型、普通 FedAvg、带保护聚合的候选方案；集中训练只可作为研究环境中的参考上限，不能在真实机构间为了对照而集中敏感数据。辩论实验至少比较单 Agent、单 Agent 自我复核、多 Agent 独立投票和有界辩论。如果简单基线以更低成本达到相同效果，就采用简单基线。所有指标按任务类型和风险分层报告，不能用大量简单查询稀释复杂任务结果。

退出条件也应事先写清：联邦模型在若干机构持续低于本地模型、隐私预算无法接受、投毒后性能失控，或辩论增加延迟却未减少关键遗漏，都意味着停止该方案。这样的“可证伪”设计比宣称两项技术必然有效更有工程可信度，也更容易回答评委对成本、隐私和幻觉的追问。

| 技术 | 核心指标 | 必须同时报告 | 失败信号 |
|---|---|---|---|
| 联邦反诈 | 固定误报率下召回、PR-AUC、未知骗局泛化 | 各机构指标、分群误报、训练成本、隐私预算 | 总分提高但小机构或特定群体误报恶化 |
| 联邦订阅识别 | 商户归一化准确率、周期识别 F1 | 冷启动、别名歧义、人工纠正率 | 把未知商户强行归类，错误传播到取消路由 |
| 多 Agent 辩论 | 关键遗漏率、无依据断言率、证据覆盖率 | 延迟、成本、分歧塌缩、正确立场被放弃率 | 共识更高但错误更多，或只增加话术长度 |
| 跨场景安全 | 越权步骤数、缺失确认数、不可逆副作用漏报 | 提示注入、恶意证据、超时和降级测试 | 任一写操作绕过确定性校验或用户确认 |
| 用户体验 | 有效提醒率、用户纠正率、人工复核完成率 | 打扰频次、解释可理解性、退出是否便利 | 风险提醒增加但用户大量关闭或误解 |

## 6.2 红队与审计样本

联邦侧应构造标签噪声、恶意参与方放大更新、后门模式、非 IID 极端分布、节点掉线和模型回滚样本，检验鲁棒聚合与降级是否真实有效。辩论侧应构造商户文本提示注入、伪造机构回执、多数方自信错误、少数方持有正确证据、Agent 相互复制和超时样本，检验系统是否能拒绝执行并保留少数意见。两类测试都应保存模型、提示词、证据和规则版本，确保结果可复现。

审计不保存或展示冗长隐藏思维链，而保存可验证的决策材料：使用了哪些数据、哪些证据被排除、发生了什么争议、哪条规则阻止了动作、用户最终确认了什么。监管强调模型可验证、可审核、可追溯，因此审计重点应是证据链和版本链，而非让 LLM 事后生成一段看似合理的解释。[银行保险机构数据安全管理办法](kimi-cite://web?url=https%3A%2F%2Fwww.nfra.gov.cn%2Fcn%2Fview%2Fpages%2FgovernmentDetail.html%3FdocId%3D1192311%26itemId%3D861%26generaltype%3D1 "citation")

# 七、分阶段落地建议

## 7.1 比赛原型只做两个闭环

第一阶段完成联邦风险识别实验和账单异常辩论闭环，优先复用现有数据结构与硬护栏，不重写六场景。联邦侧使用明确标注的合成三方数据，输出模型卡和对比结果；辩论侧接入只读证据包，输出结构化争议和裁决。第二阶段再接入跨场景 `link_chain` 的计划审查，第三阶段才考虑联邦订阅识别。真实机构联邦、生产差分隐私参数和跨机构合同治理不属于比赛原型可以虚构完成的事项。

现有试用版只有转账、订阅整理和赎回筹资付款三条工作流，账单与跨场景仍主要在文档层。因而代码实施顺序不应直接从“大而全中台”开始：先建立独立的实验与证据接口，再把通过验证的风险证据接入转账，把通过验证的辩论裁决接入计划确认。未通过对照实验的功能只保留为研究展示，不进入默认业务路径。

| 阶段 | 交付物 | 可以声称 | 不可以声称 |
|---|---|---|---|
| P0 理论与样本 | 特征 Schema、标签规范、威胁模型、合成数据卡 | 完成技术选型与实验设计 | 已解决真实跨机构数据协作 |
| P1 联邦实验 | 三方训练、基线对比、模型卡、攻击与回滚测试 | 在指定合成数据集上观察到某结果 | 零泄露、生产准确率、真实银行已接入 |
| P1 辩论实验 | 只读证据包、三方两轮协议、审计日志、基线对比 | 在指定测试集上减少某类遗漏 | 消除幻觉、多数一致即正确 |
| P2 场景接入 | 账单异常复核、跨场景计划审查、降级路径 | 作为辅助证据和只读审查 | 自动封禁、自动解冻、自动退订 |
| P3 生产验证 | 真实机构治理、影响评估、隐私与公平审计 | 经机构评审后的限定能力 | 以比赛 Demo 替代生产合规 |

## 7.2 最终推荐边界

**联邦学习首发“转账＋账单”，多 Agent 辩论首发“账单＋跨场景”，订阅复用，理财和卡片只做受限辅助。**同龄消费分位继续采用安全聚合与差分隐私；AA、费用和赎回到账使用确定性计算；C/R 适当性、信用卡审批、司法冻结、实际退订和资金状态使用规则或官方回执。这个边界既保留两项技术的亮点，也避免把原有合规设计重新交给概率模型。

如果只能各选一个演示，联邦学习选“单机构未见过的新型诈骗模式”，多 Agent 辩论选“联邦高风险与个人正常节律冲突的账单复核”。两者在同一个案例中自然衔接，又能分别独立验证，不需要把六项业务全部改成多 Agent，更不需要让联邦模型参与每一次对话。

> 本报告用于比赛产品的技术研究与设计，不构成法律、合规、投资或生产安全意见。真实展业需要持牌机构完成个人信息保护影响评估、模型风险评审、机构间责任约定、通道联调和持续审计。
