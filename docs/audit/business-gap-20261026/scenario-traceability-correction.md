# 226项清单与路演场景的来源复核

2026-10-26。用户指出拆分后的清单可能没有保住原文路演。核对结果：226项不是10份最终稿按原有场景严格一一对应的等价清单，不能据此承诺逐项做完即可完成原稿路演。本轮未按该表开发，也未重新编排原表。

## 已确认的问题

1. 将用户可见业务、实现方案、异常/校验分支、测试工具和资料任务混为同一级；“226项最小业务能力”的表述过强。
2. 只保存task ID/章节来源，没有“原稿演示场景→每个用户步骤→对应实现→完整结果/验收”的可追踪关系。条目各自存在并不代表场景可以连贯演示。
3. 第152项“账单洞察卡携上下文进入订阅处理”被排第二档。但账单稿670行已把取消订阅写进第一幕，订阅稿534行也要求与发现段无缝衔接。按用户优先做五个业务场景的决定，这段必要接力不能等独立跨场景旗舰才做。
4. 21“可控沙箱时间推进”、22中的“任务领取”是工程设计选择，不是文稿限定的实现架构。另须纠正上条解释过宽之处：理财稿743行确写“收尾：时间快进半年”，属于演示叙事要求；并不因此要求统一可控时钟平台，但不能笼统说原文没有快进安排。
5. 原文候选、P2声明及后续研究与当前主线并列编号，容易误读成全部必做，也会稀释用户要求的优先级。

## 应用边界

这是来源与规划方法纠正，不是新增业务授权或新实现证据。原稿有内部矛盾须登记而不能机械照抄，例如订阅演示台词提到未打开App，但正文禁止无授权采集App使用行为；应保留“用户确认闲置”的已定边界。纯展示快进、模拟时钟或参数化样本等实现方案需区分，不先指定平台化改造。

建议的新表结构是：主表列原稿可完整演示的用户场景及入口/终点；子表列保住该场景的缺失步骤与已有代码；技术实现、异常用例、候选和安全声明另作附表。业务场景内的必要模块接力随该场景交付，事件驱动与独立旗舰编排才属于第二档。226项仅作拆解底稿，不作为按号施工顺序。
