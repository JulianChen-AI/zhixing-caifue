## 建议先修复的顺序（未实施）

1. **先统一冲突口径**：安全D1低风险语音确认与E0全写操作手动确认；CM-C08方向不对称身份链；普通人工转账与持续规则的不同阈值。数字是方案参数，不是本轮核实过的监管常数。
2. **补确定性漏项**：申购成年/课程门槛、当日撤单窗口、目标修改重算、AA限额/次数、现金净额真实计算。保留已有幂等、旧授权失效和pending不算结算的正确边界。
3. **补任务兑现层**：用明确标注的沙箱时钟或调度器，让规则/续费提醒/观察期真正触发，验证成功、余额不足、失败停止、重复触发、取消与改口。
4. **把账单→订阅做成一个完整闭环**：流水分类/异常/周期发现→月报洞察→用户确认→解约→停扣结果，不继续靠增加目录项代替运行。
5. **补财富鹅与一条旗舰联动**：选择一个分支投教剧本和可核实成长反馈，再选一个事件驱动案例完整跑通；不要同时铺四条半成品。
6. **两项研究单独验证**：先交三方联邦和有界辩论的对照实验与证据接口；简单基线不输就采用简单方案，不为技术亮点重写全部业务。

## 不能混淆的状态

- 银行沙箱协议解除 ≠ 商户退订 ≠ 实际停扣；当前外部待办不冒充成功的边界应保留。
- 保存规则 ≠ 到期执行；保存提醒 ≠ 已推送；受理pending ≠ 份额/资金已确认。
- 取消剩余计划 ≠ 补偿回滚已执行业务；不能承诺撤回已到账资金。
- 静态种子有分类/异常/订阅 ≠ 引擎已经从新流水识别。
- 同会话持久化/恢复 ≠ 30天跨会话主动挂念；后台log ≠ 用户可检索历史链审计。
- 无真实银行/跨机构连接不等于比赛沙箱应全部判零；缺沙箱流程本身才计业务未完成。
- P1候选、P2只讲不做、原生端专有能力不与本轮MVP缺口混算。
